## Using the API

- **Base URL:** your instance URL followed by `/api/v1`, for example `https://your-pipeshub-instance.com/api/v1`.
- **Authentication:** send `Authorization: Bearer <token>` with a [personal access token](/developer/personal-access-tokens) or an [OAuth 2.0](/developer/oauth2) access token.
- **Full reference:** every instance serves an interactive API reference at `/api/v1/docs`. Use it for every endpoint, field and response. The OpenAPI spec is the [OpenAPI file](https://github.com/pipeshub-ai/pipeshub-ai/blob/main/backend/nodejs/apps/src/modules/api-docs/pipeshub-openapi.yaml) on GitHub.
- **Errors:** an error response has an `error` object with `code`, `message` and `requestId`. A missing or invalid token returns `401`; a token without the required scope returns `403`.

### Totals that stop counting

The Knowledge Hub listings (`GET /knowledgeBase/knowledge-hub/nodes` and `GET /knowledgeBase/knowledge-hub/nodes/{parentType}/{parentId}`) can return a total that is a lower bound. This happens only when the knowledge graph is stored in PostgreSQL; the other graph stores count exactly and do not send these fields. A total only ever counts rows you are allowed to read. It stops early in these cases:

- **At 10,000.** When PipesHub can count a connector's rows from the access it has already worked out for that connector, the count is exact up to 10,000 and stops there.
- **After the first 500 rows.** Otherwise, the total is the rows you may read among the first 500 it looks at. This applies to a connector PipesHub cannot count that way yet, to a listing with more than 200 rows whose access has to be checked one at a time, and to the folder tree (`onlyContainers=true`). Such a total can be well below 500.
- **An expand arrow not yet decided.** A browse lists a record you may open even when it ran out of time to decide whether the record's arrow should show. The total is then marked as a lower bound too.
- **Several connectors at once.** A search or a filtered listing adds up each connector's total, so `totalItems` can be above 10,000. It is a lower bound when any connector's total is.

What the fields mean:

- `pagination.totalCapped` is `true` when `pagination.totalItems` is a lower bound.
- `counts.capped` (with `include=counts`) is `true` when `counts.total` and the per-type counts are lower bounds.
- `pagination.totalPages` is `ceil(totalItems / limit)` for a page asked for by number. For a page asked for with `cursor`, `totalPages` and `page` are `null`.
- Use `hasNext` and `nextCursor` to tell whether another page exists, not `totalPages`.
- Older servers do not send `totalCapped` or `capped`. Treat a missing value as `false`.

In the web app, a capped total reads "Showing 1-50 of at least 500", and the page marker reads "1 / 10+" instead of "1 / 10".

## Common request bodies

These examples cover the first calls most integrations make. Field names come from the OpenAPI spec; see it for the optional fields.

<AccordionGroup>

<Accordion title="Create a knowledge base: POST /knowledgeBase">

Needs `kb:write`. `kbName` is required.

```bash
curl -s -X POST "$PIPESHUB_URL/api/v1/knowledgeBase" \
  -H "Authorization: Bearer $PIPESHUB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"kbName": "Engineering handbook"}'
```

</Accordion>

<Accordion title="Create a folder: POST /knowledgeBase/{kbId}/folder">

Needs `kb:write`. `folderName` is required.

```bash
curl -s -X POST "$PIPESHUB_URL/api/v1/knowledgeBase/KB_ID/folder" \
  -H "Authorization: Bearer $PIPESHUB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"folderName": "Runbooks"}'
```

</Accordion>

<Accordion title="Upload files: POST /knowledgeBase/{kbId}/upload">

Needs `kb:upload`. A `multipart/form-data` request. Send each file as a `files` part (up to 1000 per request). Records are named after their files.

The response streams progress as server-sent events: one `file:succeeded` or `file:failed` event per file with its `recordId`, then a `done` event with a `summary` of `total`, `succeeded` and `failed`.

```bash
curl -s -X POST "$PIPESHUB_URL/api/v1/knowledgeBase/KB_ID/upload" \
  -H "Authorization: Bearer $PIPESHUB_TOKEN" \
  -F "files=@./deploy-guide.pdf" \
  -F "files=@./oncall.md"
```

</Accordion>

<Accordion title="Start a conversation: POST /conversations/create">

Needs `conversation:chat`. `query` is required. Use `POST /conversations/stream` with a `chatMode` to stream the answer instead; see the [API Quickstart](/developer/api-quickstart).

```bash
curl -s -X POST "$PIPESHUB_URL/api/v1/conversations/create" \
  -H "Authorization: Bearer $PIPESHUB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"query": "What is our on-call rotation?"}'
```

</Accordion>

<Accordion title="Create an agent: POST /agents/create">

Needs `agent:write`. `name` is required.

The default `MCP_SCOPES` does not include `agent:write`, so a personal access token cannot hold it and this call returns `403`. Add `agent:write` to `MCP_SCOPES` on the backend before you create the token. See [Personal Access Tokens](/developer/personal-access-tokens).

```bash
curl -s -X POST "$PIPESHUB_URL/api/v1/agents/create" \
  -H "Authorization: Bearer $PIPESHUB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Support assistant",
    "description": "Answers support questions from the help center",
    "instructions": "Answer from the connected knowledge only and cite sources."
  }'
```

</Accordion>

</AccordionGroup>
