This page answers two questions for each connector: who in PipesHub can see what it syncs, and how soon a change in the source app shows up in search, chat and agents.

## How access is checked

- **At query time, against synced permissions.** When someone searches, chats or runs an agent, PipesHub checks their access in its own graph database. It does not ask the source app at that moment. The permissions it checks are the ones it last synced from the source, matched to PipesHub users by email address.
- **Permission checks fail closed.** If PipesHub can't check which records a user may see, it shows no results and says so, instead of showing everything.
- **Results are cached briefly.** The list of records each user can see is cached for up to 300 seconds. A sync that changes access clears the cache, so the limit only matters if that fails. Set `PIPESHUB_ACCESSIBLE_RECORDS_CACHE_TTL` (in seconds) to change it. See [Environment variables](/deployment/environment-variables).

## How changes reach PipesHub

- **A scheduled sync is incremental.** It picks up from where the last run stopped and reads what changed since. How it finds the changes depends on the source: a change feed, an audit log, a modified-since date, or a full listing compared with what PipesHub already holds. The tables below say which.
- **Some changes are only picked up by a full sync.** Some sources don't report every deletion or every removed share. A record deleted, or an access removed, in such a source stays in PipesHub until the next full sync. At the end of a full sync that read the whole source, PipesHub removes every record and grant the run did not see.
- **A full sync runs only when:**
  - an admin starts one (see [How to force a full sync](#how-to-force-a-full-sync)),
  - the connector's sync filters change, or
  - an earlier full sync was interrupted, so the next run finishes it.

  A scheduled run is never a full sync on its own.
- **A full sync that could not read everything removes nothing.** If part of the source couldn't be read, PipesHub keeps what it already had rather than treating the unread part as deleted. It retries on a later full sync.

## Reading the tables

- **Who sees records:**
  - **Per item**: PipesHub syncs each item's sharing from the source, and only people who can see the item there can see it in PipesHub.
  - **Everyone with the connector**: the source has no per-item access that PipesHub reads. Everyone who can use a team connector sees all of its records.
  - **Only you**: a personal connector, visible only to the person who set it up.
- **Groups**: whether the source's groups, teams or roles are synced as groups in PipesHub. **Nested** means members of child groups are included.
- **Scheduled run reads**: what an incremental run reads.
- **Interval**: the interval the sync settings start with when you choose **Scheduled**. You can change it. **Manual** means PipesHub syncs only when someone starts a sync.
- **Next full sync**: the change waits for the next full sync.

## How to force a full sync

Run a full sync after you change sharing or delete content in a source that only reports those changes to a full sync, or when search results don't match the source.

<Steps>
  <Step title="Open the connector">
    Go to **Workspace → Connectors** (or **Your connectors** for a personal connector) and find the connector's card.
  </Step>
  <Step title="Start the full sync">
    Click **Full sync**, then **Confirm**. If a normal sync is running, the button is disabled: stop that sync first.
  </Step>
</Steps>

While it runs, the button becomes **Stop full sync**. A full sync reads the whole source again, so it takes longer than a normal sync.

Over the API, send `POST /api/v1/connectors/{connectorId}/resync` with `{"connectorName": "<connector type>", "fullSync": true}`. The token needs the `connector:write` scope (`kb:write` is also accepted). See [Connector manager](/system-overview/connector-manager).
