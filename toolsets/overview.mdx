## What are Actions?

Actions are collections of tools that let AI agents **do things** in external applications. Each action provides a set of tools that agents can use to read data, create content, and perform operations in connected services.

**Use Actions when you want agents to take action on data**: sending emails, creating tickets, updating documents, or modifying content in external services.

**Key characteristics:**
- **Two-way API access**: Read and write data in real-time
- **Action-oriented**: Send emails, create tickets, update documents
- **OAuth callback URL required**: Secure authorization flow
- **Instant execution**: Actions happen immediately when agents invoke tools

Unlike **Connectors** (which index data for querying and search), **Actions** provide real-time API access for performing actions.

<Info>
  Need to search or query through documents or emails? You need [**Connectors**](/connectors/overview) instead. Connectors index data for knowledge retrieval, while actions let agents do things in other apps.
</Info>

<Note>
  **When you want to use both Connector and Action:** In the Agent Builder add nodes from **Knowledge** (Collections, API Apps) for document search and context retrieval, and add nodes from **Tools** for performing actions. Connect both to your Agent node so the agent can search context and take action in the same conversation.
</Note>

| Feature | Connectors | Actions |
|---------|------------|----------|
| **Purpose** | Sync and index data for search | Perform actions via API |
| **Data Flow** | One-way (import) | Two-way (read/write) |
| **Use Case** | Query/search data | Actions on data |
| **Real-time** | Periodic sync | Instant API calls |

## Available Actions

Tool counts come from the actions themselves.

Every agent also gets a set of **built-in capabilities** it did not have to be given.
They do not appear under **Workspace settings → Actions** and there is nothing to
configure. They are listed here so you know what an agent can already do before you
attach anything.

| Built-in capability | What the agent can do |
|---|---|
| Artifact Manager | Save and retrieve versioned output (7 tools) |
| Internal Tools | Ask the user a structured question with options (1 tool) |
| Calculator | Exact arithmetic, date differences and text counts (5 tools) |
| Date Calculator | Weekend and holiday dates for working-day maths (3 tools) |
| Image Generator | Generate or edit an image from a prompt (1 tool) |

Two of these change how you write a prompt. **Calculator** exists because language
models are unreliable at arithmetic, so an agent that must produce exact numbers
should be told to use it. **Image Generator** needs an image model configured under
**Workspace → AI Models → Image Generation** before it will work.

One more is added only when the agent has knowledge attached to it. **Knowledge
Graph** (10 tools; a few are available only when the matching deployment setting is on) lets the agent search indexed content and walk the structure it
sits in. An agent with no knowledge sources does not get it, because there would be
nothing to search.

<Warning>
**Agents can run code.** When code execution is enabled (it is by default),
an agent gets `run_code`, `install_packages` and `read_sandbox_file`, letting it
execute Python, TypeScript and SQL in an isolated sandbox. Set
`PIPESHUB_ENABLE_CODE_EXECUTION=false` to turn this off for the deployment.

These are not actions you attach, and they are not the `coding_sandbox` or
`database_sandbox` entries in the repository. Those are always excluded from agents
in favour of `run_code`.
</Warning>

<Note>
Two kinds of action are deliberately absent from **Actions**, for different reasons.

**Internal actions** (the first group above) are excluded by design. They are
attached to every agent already, so there is nothing to configure.

## Configuring Actions

### Step 1: Open Actions

Go to **Workspace settings → Actions**. Team-wide actions live there and require an
administrator; your own live under **Your actions**, which filters by
**All**, **Authenticated** and **Not authenticated** rather than by configuration
state.

  <img
    src="/images/toolsets/navigate-to-toolsets.png"
    alt="Navigate to Actions"
    className="block mx-auto w-11/12"
  />
</div>

### Step 2: Browse Available Actions

The Actions page has two sections. **App actions** lists the built-in integrations on this page, such as Slack or Jira. **API actions** lists internal REST APIs added from an OpenAPI spec; see [API actions](/agent-guide/api-actions).

The **App actions** list filters by configuration state:

- **All**: every action in the catalogue
- **Configured**: the ones already set up
- **Not configured**: the ones still to authorise

<div className="text-center">
  <img
    src="/images/toolsets/toolsets-page-new.png"
    alt="Actions page listing app actions to set up"
    className="block mx-auto w-11/12"
  />
</div>

### Step 3: Configure an Action

1. Find the action you want to configure under the **Not configured** filter
2. Click **Set up** on the action card
3. The **Action configuration** dialog opens

<div className="text-center">
  <img
    src="/images/toolsets/config-dialog-new.png"
    alt="Action configuration dialog for Confluence"
    className="block mx-auto w-11/12"
  />
</div>

### Step 4: Authenticate

Follow the authentication flow for the action:

1. Enter the required credentials in the configuration dialog (e.g., Client ID and Client Secret, or Username and Password)
2. Click **Create**, then click **Authenticate** on the new instance
3. For OAuth actions, a popup window opens for authorization
4. Grant the requested permissions (OAuth flow)
5. You'll be redirected back to PipesHub with authentication confirmed

<Info>
  Each action may have different authentication requirements. See individual action documentation for specific setup steps and credentials needed.
</Info>

### Step 5: Verify Configuration

Once configured, the action will appear under the **Configured** filter with an "Authenticated" status.

<div className="text-center">
  <img
    src="/images/toolsets/authenticated-toolset.png"
    alt="Authenticated Action"
    className="block mx-auto w-11/12"
  />
</div>

### Managing Action Configuration

You can manage your action by clicking on it under the **Configured** filter and clicking **Manage configuration** on its instance. Available actions:

- **Save**: Modify credentials or settings
- **Authenticate**: Refresh authentication if it expires or encounters issues
- **Delete instance**: Remove the action configuration entirely

## Using Actions in Agents

Once an action is configured, it becomes available in the Agent Builder:

1. Open the **Agent Builder** (create new or edit existing agent)
2. In the left sidebar, expand the **"Tools"** section
3. Find your configured action and drag it onto the canvas
4. Connect it to your agent flow

</Warning>

## Tool approvals

Each tool says what it does to data, and that decides whether it runs straight away.

- **Tools that read** run.
- **Tools that change data**, like creating a Jira issue, posting to Slack or adding a row to a spreadsheet, run.
- **Tools whose action can't be undone** ask first. That means deleting data (including a Google Docs `batch_update_document` call that does more than add or restyle content or replace literal text with non-empty text), clearing a sheet's values, sending email, and creating or changing a calendar event, which emails the attendees. A database query asks first unless it's a single plain read, insert or update, so `DELETE`, `DROP`, `TRUNCATE` or several statements in one query ask.
- **In a chat in the PipesHub app**, the person sees an approval card and chooses **Allow** or **Deny**.
- **Where nobody can answer a card** (the Slack bot, the API, the PipesHub MCP server and service-account agents), a tool that asks first doesn't run.

In the Enterprise Edition, an admin can set these rules for the whole organization, per action and per tool, in the action's **Tool approvals**: **Pre-approved**, **Allow on approval** or **Deny**. For example, an admin can make a tool that changes data ask first, or pre-approve a tool that can't be undone for an automation that needs it.

## Authentication Types

### OAuth 2.0

OAuth 2.0 is the recommended authentication method for most actions. It provides:

- **Secure token-based access**: No passwords stored
- **Automatic token refresh**: Tokens are refreshed automatically
- **Granular permissions**: Only request necessary scopes
- **User authorization**: Users explicitly grant access

**Requirements:**
- Create an OAuth application in the service's developer console
- Configure redirect URI (provided by PipesHub)
- Obtain Client ID and Client Secret

### Basic Auth

Basic Auth is used by actions like MariaDB. It works as follows:

- **Per-user credentials**: Each user enters their own username and password
- **Secure credential handling**: Credentials are stored securely and scoped to the authenticated user
- **Admin and user separation**: Admin creates the shared action instance; users authenticate their own accounts
- **No credential sharing**: One user's credentials are not visible to other users

**Requirements:**
- Admin creates the action instance (host, port, database)
- Each user provides valid username and password for that data source

## Frequently Asked Questions

<AccordionGroup>

<Accordion title="What's the difference between Connectors and Actions?">

| Aspect | Connectors | Actions |
|--------|-----------|----------|
| **Purpose** | Sync and index data for search | Enable agents to perform actions |
| **Data Flow** | One-way (import data into PipesHub) | Two-way (read and write via API) |
| **When to Use** | Query/search data | Perform actions on data |

**Example:** Use a **Gmail Connector** to index and search your email history. Use a **Gmail action** to send new emails through an agent.

</Accordion>

<Accordion title="When should I use a Connector vs an Action?">

**Connector**: Use when you need document context search: connectors sync and index your documents, emails, and pages so your assistant can find and use that context, and they do not perform actions.

**Action**: Use when the agent needs to do something in another app: create or update content, send messages, or run analytical queries (e.g. JQL, CQL, reports).

**Quick takeaway:** Search & context → **Connector**. Do something in another app → **Action**.

</Accordion>

<Accordion title="Where do I find the callback URL to add in the OAuth app?">

The callback URL is displayed in PipesHub when configuring an action:

1. Go to **Workspace > Actions**
2. Click **Set up** on the action you want to configure
3. Copy the **Redirect URI** shown in the dialog
4. Add it to your OAuth app's allowed redirect URIs in the service's developer console

The callback URL must match exactly between PipesHub and the OAuth app for authentication to succeed.

</Accordion>

<Accordion title="What OAuth scopes do Actions require?">

Actions need **read, write and delete permissions** to perform actions on your behalf:

- **Read permissions**: Access existing data (messages, tickets, files)
- **Write permissions**: Create and update content (send emails, create tickets)
- **Delete permissions**: Remove items (delete messages, delete comment)

The required scopes depend on what actions your agents will perform. Check each action's documentation page for the complete list of required scopes based on your use case.

</Accordion>

<Accordion title="Why can't I drag and use an Action in Agent Builder?">

Actions appear in the Agent Builder but can only be used after authentication:

1. Check **Workspace > Actions** for the authentication status
2. If not "Authenticated", click **Authenticate** and complete the OAuth flow
3. If expired, click **Authenticate** again
4. Return to Agent Builder and the action will be available to drag and connect

Unauthenticated actions are visible but cannot be added to agents.

</Accordion>

</AccordionGroup>
