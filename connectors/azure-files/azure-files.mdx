## What is this?

Azure File Shares is Microsoft's cloud version of a shared network drive — the kind of thing your company might call the "S: drive" or "team share".

This connector copies those files into PipesHub so you can **search them from the PipesHub chat and knowledge base**, just like any other document.

You do **not** move or delete anything in Azure. PipesHub only reads the files.

### How Azure organises your files

Three words you'll see again and again:

| Word | Means |
|------|-------|
| **Storage account** | Your top-level Azure storage. Like a house. |
| **File share** | One shared drive. You can have many per storage account. |
| **Directory / file** | Regular folders and files, just like on your laptop. |

When you set up this connector, PipesHub will read the files from the shares you pick.

### What you need before you start

1. An Azure account with access to a Storage account that contains file shares.
2. One way for PipesHub to sign in. It only lists and reads files, so give it no more than that:
   - **A SAS connection string** (recommended) for the File service, with only **Read** and **List** permissions.
   - **An account key connection string** from **Access keys**. This works too, but the key gives full read, write and delete access to everything in the storage account.
   - **Microsoft Entra ID**: an app registration with a client secret and the **Storage File Data Privileged Reader** role.

   Both connection strings need permission to view the storage account's keys (usually Owner or Contributor role).
3. A PipesHub account where you can add connectors.

That's it. You don't need to install anything.

### Step 1 — Get a credential from Azure

The **connection string** is one long password-like line that tells PipesHub how to reach your storage. We just need to copy it. A read-only SAS connection string is the safest choice. To sign in with an app registration instead, see [Microsoft Entra ID](#microsoft-entra-id) below.

#### Read-only SAS connection string (recommended)

1. Go to [https://portal.azure.com](https://portal.azure.com), sign in, and open the storage account that holds your file share.
2. In the left menu, click **Security + networking → Shared access signature**.
3. Under **Allowed services**, tick **File** only.
4. Under **Allowed resource types**, tick **Service**, **Container** and **Object**.
5. Under **Allowed permissions**, tick **Read** and **List** only.
6. Set the **End** date. When the SAS expires, syncing stops until you paste a new connection string.
7. Click **Generate SAS and connection string**, then copy the **Connection string**.

#### Account key connection string

1. Go to [https://portal.azure.com](https://portal.azure.com) and sign in.
2. In the search bar at the top, type **Storage accounts** and click it.
3. Click the storage account that holds your file share.
4. In the left menu, click **Security + networking → Access keys**.

<div className="text-center">
  <img
    src="/images/connectors/azure-files/storage_account_access_keys.png"
    alt="Azure Access keys page"
    className="block mx-auto w-11/12"
  />
</div>

5. Under **key1**, click **Show** next to **Connection string**.
6. Click the **copy** icon next to it.

You now have the connection string in your clipboard. Don't close the tab yet — if something goes wrong you'll want to come back.

<Info>
  The same Access keys page is used for Azure Blob and Azure File Shares. If you already set up Azure Blob on this storage account with an account key connection string, you can reuse it here. A SAS made for the File service only does not work for Azure Blob.
</Info>

<Warning>
  Treat either string like a password. Anyone who gets an account key connection string can read, change and delete everything in your storage account. Don't paste it into chat, email, or a public file.
</Warning>

#### Microsoft Entra ID

1. In the Azure portal, register an app in **Microsoft Entra ID** and create a **client secret** for it.
2. On the storage account, open **Access control (IAM)** and give the app the **Storage File Data Privileged Reader** role.
3. Note the app's **Directory (tenant) ID**, **Application (client) ID** and the client secret's value.
4. Note the storage account's file endpoint, for example `https://<account>.file.core.windows.net`. It is on the storage account's **Endpoints** page.

<Note>
  Azure does not let an Entra ID app list the shares in a storage account, so the **File Share Names** list may stay empty. A sync with no shares picked lists them first and fails. To sync every share, use a SAS connection string.
</Note>

### Step 2 — Open Azure Files in PipesHub

1. In PipesHub, look at the left sidebar.
2. Under **Workspace**, click **Connectors**.
3. In the list, find **Azure Files**.
4. Click **Setup** on its tile.

A panel slides in from the right. This is where you enter your details.

---

### Step 3 — Paste your connection string

The panel opens on the first tab, **Authenticate Instance**.

<div className="text-center">
  <img
    src="/images/connectors/azure-files/authenticate_tab.png"
    alt="Authenticate Instance tab with Connection String field"
    className="block mx-auto w-11/12"
  />
</div>

1. In **Instance name**, type a short name so you can recognise it later (for example `Azure files` or `Team share`).
2. **Authentication method** — leave it on **Connection String**, or pick **Microsoft Entra ID**. You can only choose this when you create the instance.
3. For **Connection String**, paste the string you copied from Azure. For **Microsoft Entra ID**, fill in **File Endpoint**, **Tenant ID**, **Client ID** and **Client Secret**.
4. Click **Next →** at the bottom.

<Info>
  The eye icon next to the Connection String field hides and shows the value. Use it if you need to double-check what you pasted.
</Info>

<Info>
  The box at the top of the panel recommends the least-privileged credential. It also warns that share-level and NTFS folder permissions are not applied: everyone with access to the connector can search every file it syncs, and a **Team** connector shares them with your whole organisation.
</Info>

<Warning>
  If saving fails with "The AccountKey in the connection string is not a valid storage account key", the string has extra spaces or got cut off. Go back to Azure, copy the connection string again, and paste it fresh.
</Warning>

<Note>
  The file endpoint must be a public `https://` address. A connection string or File Endpoint that points to plain `http` or to a private address is refused when you turn sync on.
</Note>

### Step 4 — Choose how often to sync

The panel moves you to the second tab, **Configure Records**.

<div className="text-center">
  <img
    src="/images/connectors/azure-files/configure_tab.png"
    alt="Configure Records tab with Sync settings"
    className="block mx-auto w-11/12"
  />
</div>

Under **Sync settings** there are two choices:

- **Sync Strategy** — leave as **Scheduled** if you want PipesHub to update on its own. Pick **Manual** if you want to press a button every time.
- **Sync Interval** — how often PipesHub checks Azure for new files. **1 Hour** is a good starting point.

<Info>
  Not sure? Keep **Scheduled** and **1 Hour**. You can change it later.
</Info>

---

### Step 5 — (Optional) Narrow down what gets synced

If your file shares have lots of files you don't need, you can tell PipesHub to skip some.

Scroll to **Indexing & sync filters**. Click **+ Add filter** on the right.

A small menu opens with the fields you can filter by:

<div className="text-center">
  <img
    src="/images/connectors/azure-files/filter_fields.png"
    alt="+ Add filter menu showing File Share Names, File Extensions, Modified Date, Created Date"
    className="block mx-auto w-11/12"
  />
</div>

- **File Share Names** — pick specific shares (**In**), or leave some out (**Not In**). Search matches the start of a share name.
- **Folders** — include or exclude folders inside each share, as paths from the share root, e.g. `reports/2026`. Press Enter after each folder.
- **File Extensions** — pick file types (e.g. PDFs only)
- **Modified Date** — only files changed after / before / between dates
- **Created Date** — only files created after / before / between dates

Folders are always kept by the extension and date filters, so the folder tree stays complete.

You only need filters if one of these is true:

- You want only **certain shares** or **certain folders** (not all of them).
- You want only **some file types** (e.g. PDFs, not images).
- You want only **recent files** (say, the last year).

Common examples:

- **PDFs only** — field: *File Extensions* · operator: *In* · value: `pdf`
- **Skip images** — field: *File Extensions* · operator: *Not In* · value: `jpg, png, gif`
- **Only one share** — field: *File Share Names* · operator: *In* · pick the share

<Info>
  If you don't add any filters, PipesHub will sync every file in every share the credentials can list. That's fine for small shares. On a **Team** connector, everyone in your organisation can then search all of them, so pick only shares the whole organisation may read.
</Info>

Leave **Enable Manual Indexing** off. When it's on, synced files are not indexed for search until you choose them.

When you're done, click **Save Configuration** at the bottom of the panel.

---

### Step 6 — Turn sync on

You're now on the **Azure Files** instance page. You'll see one row (your new instance).

<div className="text-center">
  <img
    src="/images/connectors/azure-files/instance_card.png"
    alt="Azure Files instance card — sync not yet enabled"
    className="block mx-auto w-11/12"
  />
</div>

Right now it says **Sync Paused**. To start syncing:

1. Find the **Sync Enabled** toggle on the right side of the row.
2. Click it.

The status changes to **Syncing** and PipesHub starts reading your files.

When you turn sync on, PipesHub first tests the connection. It lists the shares (when **File Share Names** is empty), lists each selected share's top folder, and reads one file. If something is missing, sync stays off and the error names it: **List** on the storage account, **List** on a share, or **Read**. A selected share that no longer exists doesn't stop sync; the sync removes its files.

---

### Step 7 — Check progress

Click anywhere on the row to open the **Overview** panel on the right.

<div className="text-center">
  <img
    src="/images/connectors/azure-files/instance_panel.png"
    alt="Overview panel with Records Status tiles"
    className="block mx-auto w-11/12"
  />
</div>

Here you can see:

- **Total** — how many files PipesHub has found.
- **Failed** — files it couldn't read (usually permission or file-type issues).
- **Processing** — files it's still reading right now.
- **Not Started** — files waiting their turn.
- **Sync** / **Full sync** buttons — press if you want to run a sync right now.
- **Manage Configuration** — open the setup panel again to change credentials or filters.

You can close the panel and come back any time — the sync keeps running in the background.

That's it! 🎉 Your Azure file shares are now searchable in PipesHub.

### First sync (full scan)

The very first time, PipesHub reads **everything** in the shares you chose. Big shares take longer:

| Number of files | Roughly how long |
|-----------------|------------------|
| Under 1,000 | 5 – 15 minutes |
| 1,000 – 10,000 | 15 – 60 minutes |
| 10,000 – 100,000 | 1 – 3 hours |
| Over 100,000 | Several hours or more |

Tip: using filters (e.g. PDFs only) makes the first sync much faster.

### Later syncs (just what's new)

Azure Files has no change feed, so every sync walks the shares again, but PipesHub only processes **what changed**:

- New files — added.
- Updated files — refreshed.
- Unchanged files — skipped.
- Moved or renamed files and folders — keep their record and aren't indexed again. A renamed folder takes everything below it along.
- Deleted files and folders — removed from search. A deleted folder takes everything below it.
- Files a filter now leaves out, and shares taken out of **File Share Names** — removed from PipesHub.
- A deleted share — removed with its files. If it was picked in **File Share Names**, you get one notification; remove it from the filter if it's gone for good.

These later syncs are usually quick, even for big shares.

### When something goes wrong during a sync

PipesHub only removes files after it has read a whole share. It never removes anything because of a sign-in, permission, network or throttling error.

- **A folder or share can't be read** — its files are kept, the other shares still sync, and you get a notification naming the share. If no share could be read, the sync is marked as failed.
- **The share list can't be read** (with **File Share Names** empty) — the sync fails, nothing is removed, and you get a notification. The next sync tries again.
- **Azure refuses the credentials** (an expired SAS, a rotated account key, or a changed Entra ID client secret) — the sync stops, nothing is removed, and you get a **Credentials rejected** notification. Opening a synced file asks you to reconnect the connector.
- **Throttling** — throttled and failed requests are retried, up to 3 times, and Azure's `Retry-After` wait is honoured.

### Who can see the synced files?

When you set up the connector you picked a scope:

- **Personal** — only you can search the files inside PipesHub.
- **Team** — everyone in your organisation can search them. With **File Share Names** empty, that is every share the credentials can list.

This only controls PipesHub. It does **not** change access in Azure. Share-level permissions and NTFS folder permissions are not read, so they don't limit who can search a file in PipesHub.

### Opening files

Search results and citations open the file in PipesHub, not in the Azure portal. PipesHub streams the file from Azure, whichever credential you use.

### Indexed for search

Supported file types can be content-indexed so you can search inside them:

- Documents — **PDF**, **DOCX**, **PPTX**, **XLSX**, **ODT**, **RTF**
- E-books — **EPUB**, unless copy-protected (DRM). Their text is searchable, but they can't be previewed in PipesHub; download the book to read it
- Plain text — **TXT**, **MD**, **CSV**, **JSON**, **XML**, **HTML**
- Code — **.py**, **.js**, **.ts**, **.java**, and more
- Images — **JPG**, **PNG**, **WebP**

### Synced but not searched inside

These are stored as records but their contents aren't indexed for search:

- GIF images
- Video and audio
- Archives (ZIP, RAR, …)
- Other unsupported binary files

They still show up in results by filename.

## Troubleshooting

<AccordionGroup type="single" collapsible>

<Accordion title="I get an 'authentication failed' or 'rejected the credentials' error">

- Go back to Azure, click **Copy** on the Connection string again, and paste it fresh in PipesHub.
- Check you didn't paste an extra space or line break.
- If the account key was recently rotated in Azure, or the SAS has expired, you need a new connection string.
- With Microsoft Entra ID, check the tenant ID, client ID and client secret, and that the secret hasn't expired.
- Make sure the storage account still exists.

</Accordion>

<Accordion title="Turning sync on fails with 'the credential needs the ... permission'">

The connection test names what's missing:

- **List (service level)** — the credential can't list the storage account's shares. Pick the shares in **File Share Names**, or create a SAS with the **Service** resource type.
- **List** — the credential can't list a share. Allow **List** on the SAS, and the **Container** resource type.
- **Read** — the credential can list but not read files. Allow **Read** on the SAS, and the **Object** resource type.

With Microsoft Entra ID, check that the app has the **Storage File Data Privileged Reader** role on the storage account.

</Accordion>

<Accordion title="I can't see my shares in the filter">

- Double-check the connection string is the right one.
- Search matches the start of a share name, so type the beginning of the name.
- Make sure the storage account actually has **file shares** (the icons look like folders — not blob containers).
- With Microsoft Entra ID, Azure doesn't allow listing shares, so the list may be empty.
- Some storage accounts have firewall rules — ask your Azure admin to allow PipesHub.

</Accordion>

<Accordion title="Sync is on but I see 0 files">

- Give it a minute. The first sync on a large share takes time.
- Check your filters — they might be excluding everything.
- Make sure the connection string's storage account actually has files.

</Accordion>

<Accordion title="Sync is very slow">

- Add filters (share names, file extensions, date range) to sync only what you need.
- Very large shares (millions of files) will always take several hours on the first run. Later syncs are fast.

</Accordion>

<Accordion title="Files don't show up in search">

- Check that the file type is supported for content indexing; supported images can be indexed, while video and audio are not searchable by content.
- Wait a bit — big files take longer to index.
- Make sure the file isn't password-protected.

</Accordion>

<Accordion title="It used to work, but now it doesn't">

Usually this means the Azure access keys were changed, the SAS expired, or the Entra ID client secret changed. You get a **Credentials rejected** notification, and nothing synced so far is removed.

- Go back to Step 1 and copy the new connection string (or create a new client secret).
- In PipesHub, open the instance panel and click **Manage Configuration**.
- Paste the new credentials on the Authenticate Instance tab and save.

</Accordion>

</AccordionGroup>

## Frequently asked questions

<AccordionGroup type="single" collapsible>

<Accordion title="Can I connect more than one storage account?">
  Yes. On the Azure Files instance page click **+ Add Another Instance** and repeat the steps with the new connection string.
</Accordion>

<Accordion title="Does PipesHub change anything in Azure?">
  No. The connector only **reads** files. It doesn't upload, move, rename, or delete anything. An account key connection string would still allow changes, so prefer a read-only SAS or Entra ID.
</Accordion>

<Accordion title="What happens if I delete a file in Azure?">
  On the next sync that reads the whole share, PipesHub notices it's gone and removes it from search. Deleting a folder removes everything below it; deleting a share removes the share and its files.
</Accordion>

<Accordion title="Can I sync just one folder inside a share?">
  Yes. Add a **Folders** filter set to **Include** with the folder's path from the share root, for example `reports/2026`. The folders above it are synced too, so the tree stays complete.
</Accordion>

<Accordion title="Do Azure share or NTFS permissions apply in PipesHub?">
  No. Share-level permissions and NTFS folder permissions are not read. Who can search the files is set by the connector scope: only you (**Personal**) or your whole organisation (**Team**).
</Accordion>

<Accordion title="Is the connection string encrypted?">
  Yes. PipesHub stores it as a secret — it's not visible in logs or to other users.
</Accordion>

<Accordion title="What's the difference between Azure Files and Azure Blob?">
  Both live in the same storage account. **Blob** is object storage (flat — uses prefixes to look like folders). **Files** is a real file share with real folders, usually mounted as a network drive. Pick the connector that matches where your files actually live.
</Accordion>
