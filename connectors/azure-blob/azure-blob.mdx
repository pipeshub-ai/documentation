The Azure Blob connector brings the files in your Azure Blob Storage containers into PipesHub, so you can find them in search and chat like any other document. PipesHub only reads your files. It never changes, moves or deletes anything in Azure.

<Warning>
  PipesHub does not copy Azure permissions. Everyone who can use the connector can search every file it syncs. If you set it up as a **team connector**, that means everyone in your organization. If you set it up as a **personal connector**, only you can search the files. Use a team connector only for containers the whole organization may read.
</Warning>

## Before you start

You need:

- An Azure storage account that holds your files. In Azure, files ("blobs") sit inside **containers**, and containers sit inside a **storage account**.
- Access to that storage account in the [Azure portal](https://portal.azure.com). To create a shared access signature you need a role that can see the account's keys, such as **Owner** or **Contributor**. For Microsoft Entra ID you need to be allowed to register apps and assign roles.
- A PipesHub account that can add connectors.

## Step 1: Get a sign-in for PipesHub in Azure

PipesHub needs a way to sign in to your storage account. Pick one. Give PipesHub only read access: it never needs more.

<Tabs>
  <Tab title="Shared access signature (recommended)">
    A shared access signature (SAS) is a read-only pass to your storage account that expires on a date you choose. PipesHub uses it as a **connection string**: one long line of text that tells PipesHub where your storage is and how to sign in.

    <Steps>
      <Step title="Open the storage account">
        In the [Azure portal](https://portal.azure.com), open the storage account that holds your containers.
      </Step>
      <Step title="Open Shared access signature">
        In the left menu, click **Security + networking → Shared access signature**.
      </Step>
      <Step title="Choose the settings">
        - **Allowed services**: tick **Blob** only.
        - **Allowed resource types**: tick **Service**, **Container** and **Object**.
        - **Allowed permissions**: tick **Read** and **List** only.
        - **End**: pick the date the SAS expires. On that date syncing stops until you give PipesHub a new one.
      </Step>
      <Step title="Copy the connection string">
        Click **Generate SAS and connection string**, then copy the **Connection string**. You paste it into PipesHub in Step 2.
      </Step>
    </Steps>
  </Tab>
  <Tab title="Microsoft Entra ID">
    With Microsoft Entra ID, PipesHub signs in as an app you register, and the app gets read-only access to your files.

    <Steps>
      <Step title="Register an app">
        In the Azure portal, open **Microsoft Entra ID → App registrations → New registration**. Give it a name, such as `PipesHub`, and click **Register**.
      </Step>
      <Step title="Copy the IDs">
        On the app's **Overview** page, copy the **Directory (tenant) ID** and the **Application (client) ID**.
      </Step>
      <Step title="Create a client secret">
        Open **Certificates & secrets → New client secret**, then copy the secret's **Value**. Azure shows it only once. Note when it expires: syncing stops on that date until you add a new secret.
      </Step>
      <Step title="Give the app read access">
        Open your storage account, then **Access control (IAM) → Add → Add role assignment**. Pick the **Storage Blob Data Reader** role and assign it to the app you registered.
      </Step>
      <Step title="Copy the blob endpoint">
        On the storage account, open **Settings → Endpoints** and copy the **Blob service** address. It looks like `https://<account>.blob.core.windows.net`.
      </Step>
    </Steps>
  </Tab>
  <Tab title="Account key (not recommended)">
    The connection string under **Access keys** also works, but it holds the account key, which can read, change and delete everything in the storage account. Use a SAS or Microsoft Entra ID if you can.

    1. In the [Azure portal](https://portal.azure.com), open your storage account.
    2. In the left menu, click **Security + networking → Access keys**.
    3. Under **key1**, click **Show** next to **Connection string**, then copy it.

    <img
      src="/images/connectors/azure-blob/storage_account_access_keys.png"
      alt="Azure portal Access keys page with Show buttons next to each key and connection string"
      style={{ display: 'block', margin: '0 auto' }}
      width="95%"
    />
  </Tab>
</Tabs>

<Warning>
  Treat the connection string and client secret like passwords. Don't paste them into chat, email or shared files.
</Warning>

## Choose what to sync

All of these are on the **Configure records** tab. You can change them later.

| Setting | What it does | When to use it |
|---------|--------------|----------------|
| **Sync strategy** | **Scheduled** syncs on its own. **Manual** syncs only when you start it. | Keep **Scheduled** unless you want full control. |
| **Sync interval** | How often a scheduled sync runs. The default is **1 hour**. | Make it longer for very large accounts. |
| **Enable Manual Indexing** | On: synced files are not searchable until you choose them. Off: every synced file is made searchable. | Leave it off unless you want to pick files one by one. |
| **Folders** | Folders inside each container, such as `reports/2026`. **In** syncs only these folders (and their subfolders). **Not In** syncs everything except them. The same path applies in every container you sync. Press Enter after each folder. | When you need only part of a container. |
| **Container Names** | **In** syncs only the containers you pick. **Not In** syncs every container except those. Empty means every container the sign-in can see. | Almost always, on a team connector, to keep private containers out. |
| **File Extensions** | Sync only certain file types (**In**), or skip them (**Not In**), such as `pdf` or `png`. | To skip images, videos or other files you don't need to search. |
| **Modified Date** | Sync only files changed before, after or between dates. | To leave out old files. |
| **Created Date** | Sync only files created before, after or between dates. | Same, by creation date. |

Click **Add filter** to add **Container Names**, **File Extensions**, **Modified Date** or **Created Date**. The **Folders** filter is already there.

<Note>
  When you narrow a filter later, PipesHub removes the files it now leaves out from search.
</Note>

## What gets synced and how it stays up to date

- **What appears:** every file in the containers and folders you chose, with its folder structure. You can search inside documents (PDF, Word, PowerPoint, Excel, text, CSV, HTML and more), code files, e-books (EPUB) and images (JPG, PNG, WebP). Other files, such as videos, audio, GIFs and ZIP archives, can be found by their name only. Images are searchable by their content only if your PipesHub has an AI model that can read images: a multimodal chat or embedding model under **Workspace** → **AI models**. Without one, images and scanned PDFs (pages that are pictures, with no text you can select) are synced but not searchable.
- **Opening files:** search results and citations open the file in PipesHub's viewer, not in the Azure portal.
- **First sync:** PipesHub reads everything in scope, so a large account can take hours. Filters make it faster.
- **Later syncs:** on each scheduled sync, PipesHub picks up new and changed files and skips files that haven't changed.
- **Moved or renamed files** move in PipesHub too, without being read again, as long as the file itself didn't change. A file that was both edited and moved between two syncs shows up as a new file, and its old entry is removed.
- **Deleted files and containers** disappear from PipesHub after the next sync that finishes without errors.
- **Archive tier:** files in Azure's **Archive** tier show up but aren't searchable, because Azure can't read them. After you move one to the Hot or Cool tier, the next sync makes it searchable.
- **When something goes wrong:** a sign-in, permission or network problem never removes anything from PipesHub. You get a notification, and the next sync tries again.

## Troubleshooting

<AccordionGroup>
  <Accordion title="Saving fails, or I get a 'Credentials rejected' notification">
    Azure didn't accept the sign-in. Usually the SAS has expired, the account key was changed, or the client secret expired.

    - Copy the connection string again in Azure and paste it fresh. Make sure no spaces or line breaks came with it. If you see "The AccountKey in the connection string is not a valid storage account key", the string was cut off.
    - With Microsoft Entra ID, check the tenant ID, client ID and secret, and that the app still has the **Storage Blob Data Reader** role.
    - To enter new details, open the connector in PipesHub, open its configuration, and paste them on the **Authenticate** tab.

    Nothing already synced is removed while the sign-in fails.
  </Accordion>
  <Accordion title="Syncing won't start: 'Cannot list containers', 'Cannot list blobs in' or 'Cannot create download links for files'">
    PipesHub's check before the first sync found a missing permission. The message ends with Azure's reason.

    - **Cannot list containers**: the sign-in can't see the list of containers. Create a SAS with the **Service** resource type and the **List** permission. The **Container Names** list needs this too: you can't type container names in by hand.
    - **Cannot list blobs in** a container: give the SAS the **List** permission and the **Container** resource type.
    - **Cannot create download links for files**: with Microsoft Entra ID, give the app the **Storage Blob Data Reader** role. With a SAS, include **Read** and the **Object** resource type.
  </Accordion>
  <Accordion title="My containers don't appear in the Container Names filter">
    - Type the start of the container's name. The search matches from the beginning.
    - Check that you used the right storage account, and that it has blob containers (not file shares).
    - If the storage account has a firewall, ask your Azure admin to allow PipesHub.
  </Accordion>
  <Accordion title="Syncing is on but no files show up">
    - Give it time. The first sync of a large account can take a while.
    - Check your filters. They may leave out everything.
    - If you see a **Some containers failed to sync** or **Some files failed to sync** notification, read its reason. The next sync tries again.
  </Accordion>
  <Accordion title="A file shows up but I can't search inside it">
    - Only some file types can be searched inside (see [What gets synced](#what-gets-synced-and-how-it-stays-up-to-date)).
    - Large files take longer to become searchable.
    - Password-protected and copy-protected files can't be read.
    - A file in Azure's **Archive** tier can't be read. Move it to the Hot or Cool tier in Azure, and the next sync makes it searchable.
    - Images and scanned PDFs need an AI model that can read images. Add a multimodal chat or embedding model under **Workspace** → **AI models**, then index the files again.
  </Accordion>
</AccordionGroup>

<Accordion title="Details for administrators">
  - **Deletes:** a deleted file is removed only after a sync that lists everything in scope from start to finish. If a listing fails partway, nothing is removed on that sync. A container is removed only when Azure reports that it no longer exists, never because of a sign-in or network error.
  - **Narrowed filters:** files a narrowed **Folders** filter leaves out are removed on the next sync. Files left out by **File Extensions** or date filters are removed after the next complete listing. Files from a container that **Container Names** newly leaves out are removed on the next sync.
  - **Moves:** a moved or renamed file is read again only if it was stored without a Content-MD5 hash (some large uploads have none). A copy of a file gets its own record.
  - **Folders:** folder marker blobs and Data Lake Storage Gen2 directories appear as folders, not as empty files.
  - **Blob endpoint:** the endpoint can't point to the PipesHub server itself (such as `localhost`), a link-local address or a cloud metadata address. If your deployment sets `PIPESHUB_BLOCK_PRIVATE_ADDRESSES`, private addresses are refused too.
  - **More than one storage account:** add another instance of the connector for each storage account.
  - **Secrets:** PipesHub stores the connection string and client secret encrypted.
  - **Azure docs:** [Shared access signatures](https://learn.microsoft.com/azure/storage/common/storage-sas-overview), [Assign the Storage Blob Data Reader role](https://learn.microsoft.com/azure/storage/blobs/assign-azure-role-data-access), [Connection strings](https://learn.microsoft.com/azure/storage/common/storage-configure-connection-string).
</Accordion>
