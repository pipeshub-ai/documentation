## Overview

Zammad is an open-source, web-based helpdesk and customer support ticketing system. It provides a unified interface for managing customer communications across multiple channels including email, chat, telephone, and social media, making it ideal for support teams of all sizes.

### Zammad Data Structure

The connector understands Zammad's hierarchical data model:

- **Users** (customers and agents with role assignments)
- **Groups** (support teams/departments)
  - **Tickets** (with articles and attachments)
- **Roles** (permission sets assigned to users)
- **Knowledge Base**
  - **Categories** (hierarchical structure)
  - **Answers** (articles with translations and attachments)

### What Gets Synced

The connector indexes the following content for AI-powered search:

| Content Type | Details |
|--------------|---------|
| **Tickets** | Title, state, priority, group, owner, customer, articles (messages/replies), attachments |
| **Knowledge Base** | Categories, answers/articles with translations, and associated attachments |
| **Users** | Customer and agent profiles with emails and roles |
| **Groups** | Support team/department information |
| **Roles** | User roles and permission assignments |
| **Permissions** | Group-based access controls for tickets, role-based access controls for knowledge base |

## Configuration Guide

The Zammad connector uses **API Access Token** authentication (HTTP Token Authentication) — the recommended method by Zammad for external integrations.

<Info>
  API operations performed with the token inherit the same permissions as the user who generated it. For full access to all tickets and data, generate the token from an **admin user account**.
</Info>

#### Before you start: Elasticsearch in Zammad

<Warning>
  **Ticket sync needs Elasticsearch configured in Zammad.** The connector finds each group's tickets through Zammad's ticket search, asking for tickets by group and by last-updated date. Without Elasticsearch, Zammad falls back to a basic database search that looks for the whole request as plain text in ticket titles and messages. That search finds no tickets, and Zammad reports no error, so the sync finishes with no tickets. We tested this with Zammad 6.4 and 6.5.
</Warning>

- Zammad describes Elasticsearch as optional but strongly recommended, and notes that without it search is very limited ([Zammad software requirements](https://docs.zammad.org/en/latest/prerequisites/software.html)). For this connector it is required.
- Zammad's Docker Compose stack includes Elasticsearch by default. For a package or source install, set it up with Zammad's guide: [Connect and configure Elasticsearch](https://docs.zammad.org/en/latest/install/elasticsearch/connect-configure-elasticsearch.html).
- Not sure whether your Zammad uses Elasticsearch? See **No tickets sync but the connection test passes** under [Troubleshooting](#troubleshooting) for a quick check.

#### Before you start: API token access in Zammad

- A Zammad admin must turn on **API Token Access** under **Admin → System → API**. This needs the `admin.api` permission. Without it, Zammad rejects the token.
- The user who creates the token needs the `user_preferences.access_token` permission. Without it, the **Token Access** tab doesn't appear in their profile.

#### Step 5: Authenticate tab — enter credentials

The connector drawer in PipesHub has two tabs: **Authenticate** and **Configure records**. There is no **Authorize** tab, because the access token authenticates on its own. Start on the **Authenticate** tab.

1. In PipesHub, go to **Workspace Settings** → **Connectors**, find **Zammad**, and click **Set up** for a new instance.
2. The connector panel opens as a right-side drawer. On the **Authenticate** tab, enter:
   - **Instance name** (required) — a name to identify this connector instance
   - **Zammad Instance URL** — your Zammad instance base URL (e.g., `https://<name>.zammad.com` for hosted Zammad, or `https://support.yourcompany.com` for self-hosted)
   - **Access Token** — the token you copied in Step 4
3. Click **Next**. PipesHub validates the credentials and advances to the **Configure records** tab.

#### Step 6: Configure records tab — sync settings, filters, and indexing

On the **Configure records** tab, control how the connector syncs and what gets synced.

**Sync settings** — configure your synchronization preferences first:

1. **Sync Strategy** — `Scheduled` or `Manual`.
2. **Sync Interval** — how often to sync (default: 60 minutes).

<div className="text-center">
  <img
    src="/images/connectors/zammad/sync_settings.png"
    alt="Configure Sync Settings"
    className="block mx-auto w-11/12"
  />
</div>

<Note>
  **Scheduled sync** runs automatically at the specified intervals. **Manual sync** requires you to trigger synchronization on-demand.
</Note>

**Sync filters** — determine which content is downloaded from Zammad. Data excluded by sync filters is never downloaded.

<Note>
  When you narrow a filter, the next sync removes the tickets it now leaves out, with their attachments, from PipesHub search. Anything PipesHub can't read from Zammad stays, and the following sync tries again:

  - If the group list can't be read, no tickets are removed for leaving the group filter.
  - If some of a group's tickets can't be listed, only those tickets stay. The rest of that group and the other groups are still cleaned up.
  - If one ticket can't be read back, only that ticket stays.
</Note>

<div className="text-center">
  <img
    src="/images/connectors/zammad/sync_filters.png"
    alt="Zammad Sync Filters"
    className="block mx-auto w-11/12"
  />

Available sync filters:

1. **Enable Manual Indexing** — control indexing trigger method.
   - Enabled: records are indexed only when you manually trigger it.
   - Disabled (default): records are indexed automatically after sync.

2. **Groups** — filter tickets by support group/department.
   - Operator: `In` (include only) or `Not In` (exclude)
   - Selection: searchable dropdown of your Zammad groups
   - Leave empty to sync all groups.

3. **Modified Date** — filter by last modification date. Operators: `Is After`, `Is Before`, `Is Between`.

4. **Created Date** — filter by creation date. Same operators.

**Indexing filters** — control what synced data gets processed for AI search.

- **Index Tickets** (default: enabled) — include ticket content in search
- **Index Ticket Attachments** (default: enabled) — include files attached to ticket articles in search. Knowledge base answer attachments follow **Index Knowledge Base**.
- **Index Knowledge Base** (default: enabled) — include knowledge base articles in search

Click **Save** to save your configuration. PipesHub confirms the instance is ready with a final dialog — **"Instance is configured and ready to sync!"** — offering two choices: **I'll do it later** or **Start syncing now**.

## Supported Features

The Zammad connector provides:

- **Full content sync** — Tickets, knowledge base, attachments, users, groups, and roles
- **Incremental sync** — only fetches changes since last sync using `updated_at` timestamps
- **Batch processing** — fetches data in optimized batches for performance
- **Permission preservation** — respects group-based access controls
- **Attachment handling** — syncs file attachments from ticket articles
- **Knowledge Base sync** — syncs categories and answers with translations

## Permission Model

Zammad uses different permission models for different content types:

- **Tickets**: Group-based access controls. Users can only access tickets in their assigned groups.
- **Knowledge Base**: Answer state and category roles control access.

The connector preserves these permissions:
- **Tickets**, including internal notes, are visible in PipesHub to the members of the ticket's Zammad group. Ticket customers get no access through PipesHub.
- **Published knowledge base answers** are visible to everyone in your PipesHub organization.
- **Internal knowledge base answers** are visible to users with the category's reader or editor roles.
- **Draft and archived knowledge base answers** are visible only to users with the category's editor roles.

## Troubleshooting

<AccordionGroup>

<Accordion title="Troubleshooting" icon="circle-exclamation">

### Common Issues

**Invalid API token error:**
- Verify the API token was copied correctly without extra spaces
- Check that the token has not expired (if expiry date was set)
- Ensure the token was not revoked in Zammad
- Generate a new token if the current one is compromised or lost

**Connection refused or timeout:**
- Verify the Zammad URL is correct and accessible
- Check that your Zammad instance is running and reachable from PipesHub
- Ensure there are no firewall rules blocking the connection
- Verify SSL/TLS certificates are valid (for HTTPS connections)

**Insufficient permissions error:**
- The API token inherits the creating user's permissions
- Use an admin user's token for full API access
- Check that the user account is active and not locked
- Verify the user has access to the required groups

**No tickets sync but the connection test passes:**

This usually means Zammad has no Elasticsearch connected. The connection test only checks the URL and API token, but ticket sync relies on Zammad's search, which finds nothing without Elasticsearch (see [Before you start](#before-you-start-elasticsearch-in-zammad)).

1. Check whether Zammad has an Elasticsearch address set. Run this on the Zammad server:
   - Package install: `zammad run rails r "p Setting.get('es_url')"`
   - Docker Compose (from your Zammad compose folder): `docker compose run --rm zammad-railsserver bundle exec rails r "p Setting.get('es_url')"`

   If it prints `nil` or `""`, Elasticsearch isn't set up, and ticket search can't find tickets.
2. Set up Elasticsearch and build Zammad's search index by following [Connect and configure Elasticsearch](https://docs.zammad.org/en/latest/install/elasticsearch/connect-configure-elasticsearch.html). Building the index can take a long time on a large Zammad instance.
3. When the index is built, run a sync again from **Workspace Settings** → **Connectors** in PipesHub. Tickets should now appear.

**No data syncing:**
- Verify the connector status shows "Active"
- Check that tickets exist in Zammad within your filter criteria
- Ensure the API token user has access to the groups being synced
- Review sync logs for specific error messages

**Missing knowledge base answers:**
- Check what the API token's user can see in Zammad's knowledge base. The answers listed depend on what that user can see. Keep the knowledge base permissions from Step 3 ticked on the token.
- Drafts and archived answers sync only from categories where the user is an editor, which is the case when any of the user's roles is an editor there.
- If an answer can't be saved, the sync logs a warning and the next sync tries it again.
- Releases before 0.10.0 synced no knowledge base answers from Zammad 6.0 to 6.4. After you update PipesHub, the first sync reads the whole knowledge base, so no extra step is needed.

**Missing tickets:**
- Verify group filters aren't excluding the desired content
- Check that the API token user has access to those groups
- Verify date filters aren't too restrictive

<Warning>
  If you regenerate or revoke the API token in Zammad, you must update the configuration in PipesHub with the new token value.
</Warning>

## Connector Workflow

<AccordionGroup>

<Accordion title="Synchronization Process" icon="sync">

The Zammad connector follows a structured synchronization process to ensure all data is accurately synced and permissions are properly maintained.

### Sync Order

The connector syncs data in the following order:

1. **Users** → Sync all Zammad users with their profiles and emails
2. **Groups** → Sync support groups/departments (creates both RecordGroups and UserGroups for permissions)
3. **Roles** → Sync user roles for knowledge base access controls
4. **Tickets** → Sync tickets per group with articles and attachments
5. **Knowledge Base** → Sync categories and answers with translations

If the user list can't be read in full, group members and roles are left as they were until a later sync reads the full list.

### Full Sync vs Incremental Sync

**Full Sync** occurs when:
- First-time synchronization
- Manual full sync is triggered

**Incremental Sync** occurs when:
- Previous sync completed successfully
- Only fetches content modified since last sync
- Uses `updated_at` timestamps for change detection

**Deleted tickets**: on Zammad 6.5 and later, each sync also compares each group's tickets in PipesHub with that group's tickets in Zammad (on older versions, see below). PipesHub counts the tickets it holds in batches. Only a batch whose count comes up short, or that can't be counted, is listed, in small ticket-ID ranges.

- **Deleted in Zammad, or moved out of scope:** a ticket that Zammad confirms is deleted, or that moved outside your sync filters or into a group PipesHub doesn't sync, is removed from PipesHub with its attachments.
- **Moved to another synced group:** the ticket moves there in PipesHub.
- **Kept:** a ticket that is only missing from Zammad's search results, for example while Zammad rebuilds its search index.
- **When Zammad can't be read:** a ticket-ID range that can't be listed keeps its own tickets until a later sync can list it. The rest of the group is still compared.
- **Zammad before 6.5:** these versions can't count tickets, so the comparison lists every ticket a group holds. PipesHub does that full comparison at most once every 24 hours per group, counted from the last comparison that read the whole group and settled every missing ticket. A ticket deleted in Zammad is removed on the first sync after those 24 hours: about a day with the default hourly schedule, or later with a longer interval or manual sync. A comparison that fails partway, for example a range that can't be listed or a delete that doesn't go through, doesn't start the 24 hours, so the next sync tries again. Zammad 6.5 and later is compared on every sync.
- **Large groups:** Zammad's search pages through only about 10,000 results at once. PipesHub reads a larger group in date ranges, and in ticket-ID ranges when many tickets share one update time (for example, after a bulk edit), so no group is too large to sync.

### What Gets Processed

**Tickets**: Number, title, state, priority, group assignment, owner, customer, all articles (messages, replies, notes), attachments

**Knowledge Base**: Categories hierarchy, answers/articles with full content and translations, associated attachments

On Zammad 6.0 and later, each sync reads the whole knowledge base listing and writes only the answers changed since the last sync. It syncs the answers the API token's user can see, by category:

- **Editor** (any of the user's roles is an editor in the category): every answer, including drafts and archived answers.
- **Reader only:** internal and published answers.
- **Any other category:** published answers only.

**Attachments**: Files attached to ticket articles and knowledge base answers

**Linked records**: Linked tickets and linked knowledge base answers are kept as related records

## FAQ

<AccordionGroup>

<Accordion title="How long does the initial sync take?">
  The initial sync duration depends on several factors:
  
  - **Instance size**: Number of tickets and knowledge base articles
  - **Network latency**: Connection speed to your Zammad instance
  - **Content complexity**: Tickets with many attachments take longer
  
  **Tips to speed up initial sync:**
  - Use **group filters** to sync only the groups you need
  - Use **date filters** to exclude old tickets
</Accordion>

<Accordion title="What permissions does the API token need?">
  The following permissions must be enabled when creating the API token:
  
  - **ticket.agent** - Access the tickets as agent based on group access
  - **ticket.customer** - Access tickets as customer
  - **knowledge_base.editor** - Access the knowledge base editor features
  - **knowledge_base.reader** - Access the knowledge base reader features
</Accordion>

<Accordion title="Can I sync specific groups only?">
  **Yes**. Use the Groups filter to specify which groups to include or exclude:
  
  - **Include specific groups**: Set Operator to `In` and select the groups
  - **Exclude specific groups**: Set Operator to `Not In` and select the groups to exclude
</Accordion>

<Accordion title="Queries not returning results. What could be wrong?">

There are three common causes:

1. **Email mismatch** - The email used during connector authentication doesn't match your PipesHub account email. This causes permission issues preventing you from accessing synced data.
   - **Fix:** Reconfigure the connector and authenticate using the same email as your PipesHub account.

2. **Records show in "All Records" but not in search** - Documents display in the All Records section but don't appear in search query results.
   - **Fix:** Verify sync filters in the connector settings and ensure indexing has completed. Check that the data matches your search query criteria.

3. **Data not yet indexed** - The connector is still syncing or hasn't completed the initial indexing process.
   - **Fix:** Go to **Workspace Settings → Connectors**, check the sync status, and wait for indexing to complete.

</Accordion>
