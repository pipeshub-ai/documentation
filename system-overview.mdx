PipesHub is workplace AI you run yourself. It has three parts:

1. A **web app** in the browser — search, chat, and admin
2. An **API** — who you are, what you may see, knowledge bases, and files
3. **Python services** — sync your company apps, turn documents into searchable pieces, and answer with citations

A person in the UI and an agent on MCP see the same records. If you could not open the file in Slack, the agent cannot either.

## Follow a question through the system

<Steps>
  <Step title="You ask in the browser or through an agent">
    The [Next.js](https://nextjs.org/) app (or an MCP client) sends the question to the **Node.js API** over HTTP. Chat and search can stream the reply over SSE — a live connection, so the answer appears as it is written.
  </Step>
  <Step title="The API checks who is asking">
    It verifies the session or token, applies your permissions, and forwards the question to **Query**.
  </Step>
  <Step title="Query finds sources and writes a cited answer">
    Query looks up related records in the **knowledge graph** and similar text in **Qdrant**, then calls the **LLM you configured**. You get an answer with citations back to the original documents.
  </Step>
</Steps>

That path only works if the stores already hold your data. In the background:

1. **Connectors** pull from Slack, Drive, Jira, Confluence, and the other sources.
2. They publish new or changed records onto the **event bus**.
3. **Indexing** parses the files, turns text into vectors, and writes the graph and Qdrant.

On a local machine the bus is **Redis Streams**. In a larger deployment it is **Kafka**. The job is the same either way.

The diagram is that picture. Read it top to bottom: who talks to PipesHub, then the API and the bus, then Query / Indexing / Connectors, then the stores.

## Who talks to PipesHub

### Web app

Search, chat, and admin run in the browser as a Next.js app. The pages are not rendered by Express — that process is the API, next.

### Agents and MCP

The same API exposes [MCP](/mcp/overview) at `/mcp` (Streamable HTTP). An agent authenticates with a personal access token and is held to **your** permissions, not a shared service account.

## How work is done

### Node.js API

The API is a Node.js (Express) process. In a typical Docker install it shares a host with the web app, but it does not render the UI.

It owns accounts, permissions, knowledge bases, file upload, OAuth, personal access tokens, and `/mcp`.

If you are looking up a specific API:

- [User management](/system-overview/user-management)
- [Knowledge base](/system-overview/knowledge-base)
- [Enterprise search](/system-overview/enterprise-search)

### Modules in the API process

The diagram groups Auth, Storage, Mail, Config, Notifications, and Crawling next to the API. Those are **modules in this process**, not extra containers.

| Module | What it does |
| --- | --- |
| [Auth](/system-overview/authentication) | Sign-in: password, OTP, Google, Microsoft, SAML |
| [Storage](/system-overview/storage) | Files on disk, S3, Azure Blob, or GCS |
| [Config](/system-overview/configuration-manager) | Encrypted settings the other services read |
| [Mail](/system-overview/mail-service) | Outbound email (invites, OTP) |
| [Crawling](/system-overview/crawling-manager) | When connectors run |
| [Connector manager](/system-overview/connector-manager) | OAuth tokens and connector config in Node. Python **Connectors** does the actual sync. |

### Event bus

Connectors publish; indexing consumes. You pick the transport to match the machine:

- **Local machine** — Redis Streams (`MESSAGE_BROKER=redis`). No Kafka containers.
- **Larger deployment** — Kafka (`MESSAGE_BROKER=kafka`).

Redis is still there in both cases as cache and, by default, the encrypted config store.

### Query, Indexing, and Connectors

These three Python services sit on the event bus. Each is a FastAPI process.

**Query** answers. It reads the graph and the vector store, then calls your LLM. It does not crawl Slack itself.

**Indexing** prepares data for Query. It parses files, chunks them, embeds the text, and writes Qdrant and the graph. **Docling** is the heavier parser (PDFs, tables, OCR). Two more processes, Parsing and Extraction, stay off unless you set `USE_PARSING_SERVICE=true`.

**Connectors** talk to the outside world: OAuth, token refresh, and sync from Slack, Drive, Jira, Confluence, and the rest. New records go onto the bus for Indexing. The full list: [connectors overview](/connectors/overview).

### Embedding server

Indexing and Query need **vectors** — numbers that represent meaning, so similar text can be found later.

On a default install they call a **local embedding server** over HTTP (OpenAI-compatible `/v1/embeddings`). That box is dashed in the diagram because it is not on the event bus. If you configure a cloud embedding provider, you do not need this process.

## Where data lives

Each box along the bottom of the diagram holds a different kind of state. Defaults below are what a first install uses. Details and vendor docs: [external services](/system-overview/external-services).

| Store | What it holds | Default |
| --- | --- | --- |
| **Graph** | Records, people, and how they relate — the knowledge graph | Neo4j (`DATA_STORE=neo4j`). ArangoDB is the other option. Same features either way; services do not talk to a vendor driver. |
| **Vectors** | Embedded chunks for similarity search | Qdrant (`VECTOR_DB_TYPE=qdrant`) |
| **Documents** | Sessions, file metadata, application state | MongoDB |
| **Files** | The bytes of uploaded and connector files | Disk, or S3 / Azure Blob / GCS. See [storage](/system-overview/storage). |
| **Redis** | Cache; default encrypted config; Redis Streams when that is the bus | Always on |
| **etcd** | The other place to keep encrypted config | Off unless you set `KV_STORE_TYPE=etcd` (Compose profile `kv-etcd`) |

## Models you bring

PipesHub does not ship a hosted LLM. You point it at models you already use.

- An **embedding model** turns parsed text into vectors for Qdrant. The local embedding server is the default.
- An **LLM** writes the cited answer. Any provider, or a local model through Ollama.

The left-hand box on the diagram is that pair.

## Identity and the rest of the company

On the right of the diagram: identity providers (Azure AD, Okta, and others), SMTP for mail, and the 50+ apps connectors sync. Those are not PipesHub processes. You connect them; Auth, Mail, and Connectors call out.
