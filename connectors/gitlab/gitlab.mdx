## Overview

GitLab is a DevOps platform for hosting code, tracking work, and reviewing changes. The connector
brings your projects, work items, merge requests, and source code into PipesHub so you can search
across all of them in one place.

### GitLab Data Structure

PipesHub mirrors how GitLab organizes your content:

```
Group
└─ Project
   ├─ Work items                → comments, attachments
   ├─ Confidential work items   → comments, attachments
   ├─ Merge requests            → commits, diffs, review comments
   └─ Code repository           → folders and files
```

| Entity | Description |
|--------|-------------|
| **Group** | Groups and subgroups that own the projects beneath them |
| **Project** | The main container, split into the four sections below |
| **Work Items** | Issues, tasks, and incidents |
| **Confidential Work Items** | Work items marked confidential in GitLab, kept apart so only people allowed to see them can |
| **Merge Requests** | Proposed code changes with reviews and merge history |
| **Code Repository** | Source files and folders on the synced branch (the default branch unless you choose another) |
| **Comments** | Discussion on work items and merge requests |
| **Attachments** | Files and images added to work items, merge requests, and comments |

Splitting each project into four sections lets permissions apply to the right part of a project.
A Guest can reach a project's work items, for example, without gaining access to its confidential
work items or its source code.

### What Gets Synced

Each connector instance syncs **one project**, chosen in the **Repository** filter. To sync more
projects, add another connector instance for each one. For that project, the connector indexes the
following content for AI-powered search:

- **Project**: The selected project, and the groups and subgroups that contain it
- **Code Files**: Source files and folders on the branch chosen in the **Branch** filter, or the
  project's default branch when no branch is chosen
- **Work Items**: Issues, tasks, and incidents with title, description, status, and labels
- **Merge Requests**: Description, commits, changed files with diffs, and review comments
- **Comments**: Full comment threads on work items and merge requests with author information
- **Attachments**: Files and images attached to work items, merge requests, and comments
- **Users**: GitLab users in the groups and projects being synced
- **Permissions**: Project access controls are preserved

### Authentication Method

The **GitLab** connector offers two authentication methods. Pick one from the **Authentication
method** dropdown on the **Authenticate** tab:

| Method | Shown as | When to use it |
|--------|----------|----------------|
| **OAuth 2.0** | OAuth 2.0 | The default. You register an OAuth application in GitLab and sign in through it (Steps 1–5 below) |

### Using a personal access token

The **GitLab** connector can authenticate with a personal access token instead of OAuth 2.0. If you
use a token, skip Steps 1–5 and do this instead:

1. In GitLab, open **User settings** → **Access tokens**
   ([gitlab.com/-/user_settings/personal_access_tokens](https://gitlab.com/-/user_settings/personal_access_tokens),
   or the same path on your self-managed host)
2. Create a token with the same scopes the OAuth application uses: `read_user`,
   `read_repository`, and `read_api`
3. Set an expiry date and copy the token
4. In PipesHub, open **Workspace settings** → **Connectors**, find **GitLab**, and click **Set up**
5. Enter an **Instance name**, and under **Authentication method** choose **API Token**
6. Paste the token into **Personal Access Token**. For self-managed GitLab, also set the **GitLab
   Instance URL**
7. Continue with Step 6 below

The connector reads GitLab as the token's owner, so the token needs access to the project you
plan to sync.

<Warning>
  GitLab personal access tokens expire. When the token expires the connector stops syncing; create
  a new token and update it in the connector's **Authenticate** tab.
</Warning>

#### Sync Filters

Sync filters control **what the connector fetches from GitLab**. Anything excluded here is never
retrieved, so narrowing scope also shortens sync time.

| Filter | Type | What it does |
|--------|------|--------------|
| **GitLab Groups** | Multi-select | Narrows the **Repository** picker to projects in these groups or subgroups. Uses the namespace path, e.g. `my-org/engineering` |
| **Repository** | Single select, **required** | The one project this connector instance syncs, e.g. `my-org/my-repo`. To sync another project, add another connector instance |
| **Branch** | Single select | The branch whose files are synced. Leave it unset to follow the project's default branch |
| **Modified Date** | Date range | Only sync work items and merge requests last modified in this window (GitLab only) |
| **Created Date** | Date range | Only sync work items and merge requests created in this window (GitLab only) |
| **Exclude Paths** | List | Paths to leave out of code sync, gitignore-style: `docs/`, `**/fixtures/**`, `*.snap`. Adds to the built-in exclusions in *What is excluded from code sync*; it can't bring those back |

<div className="text-center">
  <img
    src="/images/connectors/gitlab/ph-gitlab-sync-filters.png"
    alt="GitLab connector sync filters in PipesHub"
    className="block mx-auto w-11/12"

**GitLab Groups**, **Repository**, and **Branch** are live pickers — start typing and PipesHub
queries your GitLab instance for matches. You can't save the configuration until exactly one
project is selected in **Repository**.

If the chosen branch no longer exists, code sync for the project stops and the existing code
records are kept; the connector does not fall back to the default branch. Changing the branch
re-walks the whole repository on the next sync.

The date filters apply to **work items and merge requests only**. Code files are always synced from
the current state of the synced branch, so a date filter does not narrow them.

#### Indexing Filters

Indexing filters control **what gets indexed for search** from the content that was fetched.

| Filter | Default | What it does |
|--------|---------|--------------|
| **Index Issues** | On | Index work items (issues, tasks, incidents) with their comments and attachments |
| **Index Merge Requests** | On | Index merge requests with their diffs, review comments, and commits |
| **Index Code Files** | On | Index the source files on the synced branch |
| **Index Test Files** | Off | Index test files too. When off, test files are still synced and findable by name and path, but their contents are not indexed |
| **Enable Manual Indexing** | Off | Records are synced but held unindexed until you trigger indexing yourself |

A file counts as a test file when it sits under a folder such as `test/`, `tests/`, `spec/`,
`__tests__/`, `__mocks__/`, `e2e/`, `testdata/`, or `fixtures/` (any capitalization), or when its
name follows a test convention such as `test_*.py`, `*_test.go`, `*.test.ts`, `*.spec.js`,
`*Test.java`, `*_spec.rb`, or `conftest.py`.

<div className="text-center">
  <img
    src="/images/connectors/gitlab/ph-gitlab-indexing-filters.png"
    alt="GitLab connector indexing filters in PipesHub"
    className="block mx-auto w-11/12"

Turning **Index Code Files** off is the usual choice for large monorepos where you only want issue
and merge-request context. The files are still synced and stay findable by name and path — only
their contents are left unindexed.

## Supported Features

The GitLab connector syncs the following data from the project selected in the **Repository**
filter (one project per connector instance):

- **Groups & Projects**: The selected project and the groups and subgroups that contain it
- **Code repository**: Files and folders on the synced branch (the default branch unless you choose
  another in the **Branch** filter), with language detection and full-text indexing of file
  contents
- **Work Items**: All work items (issues, tasks, and incidents) content including description, status, comments
- **Merge Requests**: Full merge request content including description, merge status, commit history, review comments, comments and file changes
- **Comments**: All comments on work items, merge requests with author information
- **Attachments**: Files attached to work items, merge requests (images, documents, etc.)
- **Users & memberships**: GitLab users and their project access levels, used to apply permissions

## Troubleshooting

<AccordionGroup>

<Accordion title="Troubleshooting" icon="circle-exclamation">

### Common Issues

**Invalid client credentials error:**
- Verify Client ID and Client Secret are correct
- Ensure you copied the full values without extra spaces
- Check that the OAuth app is active in GitLab applications
- Regenerate the secret if necessary and update PipesHub

**Callback URL mismatch error:**
- Ensure the Redirect URI in PipesHub exactly matches the callback URL in GitLab
- Check for trailing slashes or protocol differences (http vs https)
- Update both configurations to use the same URL

**Authorization failed:**
- Verify you're signing in with a valid GitLab account that has access to the required projects

**No data syncing:**
- Verify the connector status shows "Active"
- Check that a project is selected in the **Repository** sync filter and that the authorizing
  account (or the token's owner) can read it
- Review sync logs for specific error messages

**Token expired or sync stopped:**
- Disable and re-enable the connector to re-authenticate
- Check if the OAuth app is still active in GitLab applications
- If you use a personal access token, check its expiry date in GitLab and, if it has expired or
  been revoked, create a new one and update it in the connector

**No code files synced:**
- Confirm **Index Code Files** is enabled under Indexing Filters
- Verify the OAuth application (or personal access token) includes the `read_repository` scope —
  without it the connector can read issues and merge requests but not repository contents
- Only one branch is synced: the one chosen in the **Branch** filter, or the default branch when
  none is chosen. If the chosen branch was deleted, code sync stops until you pick another
- Check that the files aren't covered by the **Exclude Paths** filter or the built-in exclusions
  (see *What is excluded from code sync*)
- Test files are synced but not indexed unless **Index Test Files** is on
- Source and text files above 5 MB still appear as records, marked **File Type Not Supported**
  with the file's size as the reason; their contents are not indexed (see *How each file is
  indexed*)

**A user sees no records even though they have GitLab access:**
- Their GitLab **public email** is probably not set. Ask them to set it (see the email visibility
  prerequisite above) — the next sync will grant their permissions automatically
- Their GitLab email must match their PipesHub account email
- Guests (access level 10) can reach work items only, by design — not confidential work items,
  merge requests, or code. Planners (access level 15) also see confidential work items, but not
  merge requests or code

**Nothing syncs on a self-managed instance:**
- Verify the **GitLab Instance URL** is the base host with no trailing slash and no path
- Confirm the OAuth application was created on that instance, not on gitlab.com
- Check that the instance is reachable from the PipesHub deployment

**An admin or auditor account returns no projects:**
- EE auditor accounts hit a documented GitLab limitation where listing endpoints return nothing.
  The connector retries with a membership-scoped query, which narrows coverage. Use an instance
  administrator account for full coverage

<Warning>
  If you modify OAuth application settings in GitLab applications (Client ID, Secret, callback URL), you must update the configuration in PipesHub and re-authorize the connection.
</Warning>

</Accordion>

## Connector Workflow

<AccordionGroup>

<Accordion title="Synchronization Process" icon="sync">

The GitLab connector follows a structured synchronization process to ensure all data is accurately synced and permissions are properly maintained.

### Sync Overview

Every sync run executes the same ordered cycle:

| Step | Stage | What happens |
|------|-------|--------------|
| 1 | **User sync** | Resolve GitLab users of the in-scope groups and projects and match them to PipesHub accounts by email |
| 2 | **Project sync** | Discover projects, create the group → project → container hierarchy, and apply per-member permissions |
| 3 | **Content sync** | For each project, sync work items, merge requests, and the code repository |
| 4 | **Timestamp backfill** | A background pass fills in authoritative commit timestamps for code files after the main sync completes |

### Full Sync vs Incremental Sync

The connector automatically determines whether to perform a full or incremental sync:

**Full Sync** occurs when:
- First-time synchronization (no sync checkpoint exists)
- The previous incremental attempt failed and had to re-baseline
- Manual full sync is triggered

**Incremental Sync** occurs when:
- A valid sync checkpoint exists
- Uses the saved sync checkpoint to fetch or filter for records updated since the last sync time

### User Synchronization

1. **Scope resolution**: If Group or Repository sync filters are set, only members of those
   entities are walked — without this a connector targeting a few groups on a large instance
   would scan every group the account can see
2. **Member fetch**: Retrieves group and project members with their access levels
3. **Email enrichment**: Fetches each member's full profile to read their **public email**, then
   matches it to a PipesHub account

### Project Synchronization

1. **Project fetch**: Retrieves the project selected in the **Repository** filter
2. **Container creation**: The project becomes a record group with four children — *Work items*,
   *Confidential work items*, *Merge requests*, and *Code repository*. Parent GitLab groups are
   created above them
3. **Permission assignment**: Member access levels are translated into per-container permissions
   (see *Permission handling* below)

Containers are keyed on the project's **numeric GitLab ID**, not its path. Renaming or moving a
project between groups therefore does not orphan its records or reset its sync checkpoint.

### Code Repository Synchronization

Code sync tracks the branch chosen in the **Branch** filter, or the project's **default branch**
when none is chosen, and is checkpointed on the branch's current commit SHA. If the synced branch
changes, the next sync walks the whole tree.

**Full sync** (first run, or when the delta cannot be trusted):

1. Walks the entire repository tree, paginating through it
2. Creates a folder record for each directory and a code file record for each file, with the
   file's language detected from its path
3. Prunes records for files that no longer exist in the tree

**Incremental sync** (a checkpoint SHA exists):

1. Compares the checkpointed commit against the current branch head
2. Classifies each changed path as added, modified, deleted, or renamed — a delete-and-add pair
   for the same content is reconciled back into a **rename**, so the record keeps its identity and
   history rather than being recreated
3. Applies deletions, renames, and upserts, then removes folders left empty

#### What is excluded from code sync

Not every file on the synced branch becomes a record. The connector skips content that adds noise
without adding meaning, and never reads credential files. Excluded files get no record at all:

| Excluded | Examples |
|----------|----------|
| Dependency directories (at any depth) | `node_modules`, `bower_components`, `jspm_packages`, `vendor`, `third_party`, `thirdparty`, `site-packages`, `venv`, `.venv` |
| Caches and tool output (at any depth) | `__pycache__`, `.mypy_cache`, `.pytest_cache`, `.ruff_cache`, `.tox`, `.next`, `.nuxt`, `.svelte-kit`, `.parcel-cache`, `.turbo`, `coverage`, `htmlcov`, `.nyc_output` |
| Build output | `dist`, `build`, `target`, `out`, `bin`, `obj`, and `env` at the top of the repository. Deeper down, `dist`, `target`, and `obj` folders, and built files such as `.js`, `.class`, or `.o` inside `build` or `out` folders, unless they sit under a source folder such as `src/`, `lib/`, `app/`, or `pkg/` |
| Lock files | `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lockb`, `poetry.lock`, `uv.lock`, `Cargo.lock`, `composer.lock`, `Gemfile.lock`, `packages.lock.json`, `go.sum`, and any file ending in `.lock` |
| Minified and derived files | `*.min.js`, `*.min.css`, `*.map`, `*.snap` |
| Generated code | Protobuf output (`*.pb.go`, `*_pb2.py`), `*.g.dart`, `*.generated.*`, files under `generated/`, `__generated__/`, or `gen/` |
| Credential and key files | `.env` and `.env.*` files, `.npmrc`, `.pypirc`, `.netrc`, `.pgpass`, `.htpasswd`, `.git-credentials`, `credentials.json` / `.yml` / `.yaml`, SSH keys (`id_rsa`, `id_ed25519`), `terraform.tfstate`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.tfvars` |
| Marked in `.gitattributes` | Paths the repository's root `.gitattributes` marks `linguist-generated` or `linguist-vendored` |
| Dot-files | Any file whose name begins with `.` |
| Editor and VCS metadata | `.git`, `.hg`, `.svn`, `.idea`, `.vscode`, `.gradle` |
| Your own exclusions | Paths matching the **Exclude Paths** sync filter |

A path the root `.gitattributes` explicitly marks as not generated and not vendored (for example
`-linguist-generated`) is kept even if the built-in rules would skip it. Credential files, dot-files,
and **Exclude Paths** matches are always left out.

This keeps search results focused on code your team actually wrote. It also means the file count in
PipesHub will be lower than the file count in the repository — that is expected.

#### How each file is indexed

The files that do become records are not all source code, so PipesHub reads each one with the
reader that fits it:

| File | How it is indexed |
|------|-------------------|
| Source code in a supported language | By class, function, and method, up to 5 MB |
| `.csv`, `.tsv` | As a table, row by row, the same way as an uploaded CSV |
| `.json`, `.yaml`, `.yml` | By its structure, the same way as an uploaded JSON or YAML file |
| Other text files, such as shell scripts, SQL, and stylesheets | As plain text, up to 5 MB |
| Source or text files above 5 MB | Not indexed |
| Line-delimited JSON: `.ndjson`, `.jsonl` | Not indexed |
| Files that hold binary data under a text file name | Not indexed |
| Minified code, or a file whose first lines mark it as generated (for example `DO NOT EDIT` or `@generated`) | Not indexed |
| Git LFS pointers (the file's content is stored in Git LFS) | Not indexed |

A file that isn't indexed keeps its record and stays findable by name and path. It shows
**File Type Not Supported**, with a reason that says why:

- Above 5 MB: "This file is 12.5 MB, and PipesHub reads code and plain-text files up to 5 MB.
  Split it into smaller files, or ask your admin to raise the limit (CODE_FILE_MAX_SIZE_MB) and
  then choose Index all on the repository."
- Minified or generator-marked files: "This is a generated file (a lock file, minified bundle,
  source map, test snapshot or a file its generator marked DO NOT EDIT), so PipesHub skips it to
  keep search results useful. Nothing needs fixing."
- Git LFS pointers: "This file is stored with Git LFS, so the repository holds only a pointer to
  it, not its content. PipesHub skips the pointer. Nothing needs fixing."
- `.ndjson` and `.jsonl`: "PipesHub can't read .ndjson files yet. Convert the file to PDF, DOCX or
  TXT to make it searchable."
- Binary data: "This file holds binary data rather than text, so PipesHub can't read it. If it is
  meant to be text, commit it as plain text (UTF-8) and the next sync will index it."

Nothing is cut short: a file is either indexed whole or not at all.

<Note>
  On a self-hosted deployment, an admin can raise the 5 MB limit by setting the
  `CODE_FILE_MAX_SIZE_MB` environment variable on the PipesHub container and restarting it. The
  limit applies to source and plain-text files; CSV, JSON, and YAML files are not subject to it.

  Raising the limit doesn't index the file by itself: a file marked **File Type Not Supported**
  has no Reindex action, and a sync skips a repository that hasn't changed. To index it, open the
  project in PipesHub and choose **Index all** on its **Code repository**, which sends every file
  in it back through indexing. **Re-index failed**, on the same menu, retries only files marked
  Failed, so it leaves this file as it is.
</Note>

<Warning>
  **Deletion safety valve.** If a single tree walk returns a truncated or incomplete file list,
  applying it would delete a large fraction of the project's code records. The connector refuses
  any pass that would remove more than half of a project's files, leaving them for the next
  complete walk instead.
</Warning>

Because the checkpoint is only advanced after a successful pass, a failed sync is simply redone on
the next run. All writes are idempotent, so retrying never produces duplicates.

### Work Item Synchronization

For each project, the connector fetches **work-items and merge-requests** from the GitLab API. Each record is normalized into a **hierarchical BlockGroup layout** inside a **BlocksContainer**: the description, conversation, and (for merge requests) code-review context are kept in separate block groups so search and retrieval can target the right slice of content.

#### Body, comments, and attachments

For each **work-item and merge-request**, the connector:

- **Description**: Stores the body as the first **BlockGroup** (index 0). Markdown is preserved and inline images are embedded in the indexed representation.
- **Comments**: Stores each top-level comment as its own **BlockGroup** in thread order.
- **Attachments and images**: Applies the same extraction and **placement** rules for work-items and merge-requests—files and images are mapped to the **description** or the **specific comment** they belong to.

<Info>
  Merge requests use the same body, comment, and attachment handling as work items. The section below lists **additional** content indexed only for merge requests.
</Info>

#### Additionally for merge requests

- **Commits**: **Commit SHAs** (and related commit context) are synced as dedicated blocks so answers can be tied to the commits on the MR.
- **Changed files**: For files touched by the MR, the connector indexes **file content** together with the **diff** (patch) for that change.
- **Review comments on the diff**: **Per-file** review comments on the MR changes—including line-associated feedback where GitLab provides it—are indexed separately from regular work items / merge requests conversation comments.

#### Sync pipeline (summary)

1. **Fetch** all work items and merge requests for the project (respecting full vs incremental sync rules above).
2. **Batch** records for processing.
3. **Build BlockGroups** for description and comments; **map** attachments and images to the description or the correct comment.
4. **For merge requests only**, add blocks for commits, changed files with diffs, and review comments on changes.

<Note>
  Comments are stored as **BlockGroups** within the parent work item or merge request **BlocksContainer** (not as separate top-level records). That keeps threads organized and ensures comments are removed when the parent record is deleted.
</Note>

### Permission handling

This section applies to the **GitLab** connector. GitLab Personal syncs no memberships: everything
it syncs is visible only to the user who set it up.

Each project's member list is read from GitLab and translated into per-user permissions. Because a
project is split into four containers, a member's GitLab **access level** decides which of them
they can reach:

| GitLab role | Access level | Work items | Confidential work items | Merge requests | Code repository |
|-------------|--------------|:----------:|:-----------------------:|:--------------:|:---------------:|
| **Guest** | 10 | ✅ | — | — | — |
| **Planner** | 15 | ✅ | ✅ | — | — |
| **Reporter** | 20 | ✅ | ✅ | ✅ | ✅ |
| **Developer** | 30 | ✅ | ✅ | ✅ | ✅ |
| **Maintainer** | 40 | ✅ | ✅ | ✅ | ✅ |
| **Owner** | 50 | ✅ | ✅ | ✅ | ✅ |

Members with **Minimal Access** (access level 5) get no access in PipesHub. The author and the
assignees of a confidential work item can always see that item, whatever their role, as they can in
GitLab.

A GitLab user is matched to a PipesHub account **by email address**, which is why the email
visibility prerequisite in the Configuration Guide matters. A member whose email cannot be resolved
gets no permission edge; once they make their email visible, the next sync grants their access
automatically.

If member enumeration fails for a project, the connector falls back to granting the connector
creator alone. It never falls back to granting everyone.

**Admin and auditor accounts.** If the authenticating account is an instance administrator or an
EE auditor, the connector widens its listing scope to every project and group that account can
read, instead of only those it holds a membership row on.

<Warning>
  GitLab documents a [known issue](https://docs.gitlab.com/administration/auditor_users/) where the
  auditor flag does not actually grant read access through most listing endpoints. When an auditor
  account returns zero groups or projects, the connector automatically retries with a
  membership-scoped query and logs a warning. If you expect instance-wide coverage and see that
  warning, use an administrator account instead.
</Warning>

### Checkpoint Management

Checkpoints are stored **per project**, and each content type carries its own:

- **Work items / merge requests** — the latest update timestamp seen, so the next run only asks
  GitLab for items changed since then
- **Code repository** — the synced branch's commit SHA at the end of the last successful walk,
  used as the base of the next comparison

If saving a batch of records fails, the sweep stops there without writing its checkpoint, and
the next run lists the items again from the previous checkpoint. The code repository stage works
the same way: its checkpoint is only written after the stage succeeds.

A single issue or merge request that can't be built (for example, because its comments can't be
read) is handled differently: the rest of the project still syncs, and the checkpoint is written
just before the earliest failed item, so the next run asks for it again without re-reading
everything.

The OAuth token is refreshed ahead of its expiry by PipesHub's normal OAuth refresh. If GitLab
still answers **401 Unauthorized**, the connector refreshes once and retries; when several requests
get a 401 together, they share that one refresh, so refresh tokens aren't used up needlessly. An
error that carries any other status never triggers a refresh, even if its text mentions "401". An
error with no status at all (for example, a failure partway through a paged listing) is judged by its
text, so wording such as "401" or "unauthorized" can still trigger one refresh.

</Accordion>

## FAQ

<AccordionGroup>

<Accordion title="Queries not returning results. What could be wrong?">

Common causes:

1. **Email mismatch** - The email used during connector authentication doesn't match your PipesHub account email. This causes permission issues preventing you from accessing synced data.
   - **Fix:** Reconfigure the connector and authenticate using the same email as your PipesHub account.

2. **Data not yet indexed** - The connector is still syncing or hasn't completed the initial indexing process.
   - **Fix:** Go to **Settings > Connectors**, check the sync status, and wait for indexing to complete.

</Accordion>

<Accordion title="How long does the initial sync take?">
  The initial sync duration depends on how much content your GitLab projects hold. A record is a
  single item — a work item, a merge request, a code file, or an attachment.

  | Approx record count | Estimated time |
  |---------------------|----------------|
  | Up to 10,000 | Under 10 minutes |
  | 10,000 to 50,000 | 10 to 30 minutes |
  | 50,000 to 100,000 | 30 to 60 minutes |
  | Over 100,000 | Roughly 1 hour per 100,000 records |

  As a rule of thumb, the connector syncs about **100,000 records per hour**.

</Accordion>

<Accordion title="Why do I see no records after authenticating?">
  The most common causes are missing scopes or selecting the wrong GitLab account. Re-run authentication, ensure the PipesHub email and GitLab account emails match.
</Accordion>

<Accordion title="Can I sync several projects, or a whole group?">

Each connector instance syncs exactly **one project**, chosen in the required **Repository** filter
on the **Configure records** tab. To sync more projects, add another connector instance for each
one.

The **GitLab Groups** filter only narrows the **Repository** picker to projects in the groups you
choose; it doesn't sync a whole group. Both fields are live pickers that query your GitLab instance
as you type.

</Accordion>

<Accordion title="Does the connector sync all branches?">

No. Code files are synced from one branch per project: the branch chosen in the **Branch** filter,
or the project's **default branch** when none is chosen. Merge request diffs still capture the
changes proposed from other branches, so review discussion remains searchable, but the file records
themselves reflect the synced branch.

</Accordion>

<Accordion title="Does it work with self-managed GitLab?">

Yes. Set the **GitLab Instance URL** field to your host (for example
`https://gitlab.mycompany.com`) when configuring authentication, and create the OAuth application
(or personal access token) on that instance rather than on gitlab.com. Leave the field blank for
GitLab.com.

</Accordion>
