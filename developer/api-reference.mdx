## Using the API

- **Base URL:** your instance URL followed by `/api/v1`, for example `https://your-pipeshub-instance.com/api/v1`.
- **Authentication:** send `Authorization: Bearer <token>` with a [personal access token](/developer/personal-access-tokens) or an [OAuth 2.0](/developer/oauth2) access token.
- **Full reference:** every instance serves an interactive API reference at `/api/v1/docs`. Use it for every endpoint, field and response. The OpenAPI spec is the [OpenAPI file](https://github.com/pipeshub-ai/pipeshub-ai/blob/main/backend/nodejs/apps/src/modules/api-docs/pipeshub-openapi.yaml) on GitHub.
- **Errors:** an error response has an `error` object with `code`, `message` and `requestId`. A missing or invalid token returns `401`; a token without the required scope returns `403`.

## Common request bodies

These examples cover the first calls most integrations make. Field names come from the OpenAPI spec; see it for the optional fields.

<AccordionGroup>

<Accordion title="Create a knowledge base: POST /knowledgeBase">

Needs `kb:write`. `kbName` is required.

```bash
curl -s -X POST "$PIPESHUB_URL/api/v1/knowledgeBase" \
  -H "Authorization: Bearer $PIPESHUB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"kbName": "Engineering handbook"}'
```

</Accordion>

<Accordion title="Create a folder: POST /knowledgeBase/{kbId}/folder">

Needs `kb:write`. `folderName` is required.

```bash
curl -s -X POST "$PIPESHUB_URL/api/v1/knowledgeBase/KB_ID/folder" \
  -H "Authorization: Bearer $PIPESHUB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"folderName": "Runbooks"}'
```

</Accordion>

<Accordion title="Upload files: POST /knowledgeBase/{kbId}/upload">

Needs `kb:upload`. A `multipart/form-data` request. Send each file as a `files` part (up to 1000 per request). Records are named after their files.

The response streams progress as server-sent events: one `file:succeeded` or `file:failed` event per file with its `recordId`, then a `done` event with a `summary` of `total`, `succeeded` and `failed`.

```bash
curl -s -X POST "$PIPESHUB_URL/api/v1/knowledgeBase/KB_ID/upload" \
  -H "Authorization: Bearer $PIPESHUB_TOKEN" \
  -F "files=@./deploy-guide.pdf" \
  -F "files=@./oncall.md"
```

</Accordion>

<Accordion title="Start a conversation: POST /conversations/create">

Needs `conversation:chat`. `query` is required. Use `POST /conversations/stream` with a `chatMode` to stream the answer instead; see the [API Quickstart](/developer/api-quickstart).

```bash
curl -s -X POST "$PIPESHUB_URL/api/v1/conversations/create" \
  -H "Authorization: Bearer $PIPESHUB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"query": "What is our on-call rotation?"}'
```

</Accordion>

<Accordion title="Create an agent: POST /agents/create">

Needs `agent:write`. `name` is required.

The default `MCP_SCOPES` does not include `agent:write`, so a personal access token cannot hold it and this call returns `403`. Add `agent:write` to `MCP_SCOPES` on the backend before you create the token. See [Personal Access Tokens](/developer/personal-access-tokens).

```bash
curl -s -X POST "$PIPESHUB_URL/api/v1/agents/create" \
  -H "Authorization: Bearer $PIPESHUB_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Support assistant",
    "description": "Answers support questions from the help center",
    "instructions": "Answer from the connected knowledge only and cite sources."
  }'
```

</Accordion>

## Paging a navigate listing

`GET /connectors/navigate` lists what is under a node of the knowledge graph (a source, record group, folder or record), or everything you can read when you send no `nodeId`. It needs `kb:read` or `connector:read`. Each response carries a `pagination` object:

| Field | Meaning |
| --- | --- |
| `has_next` | `true` while more children follow. Keep paging until it is `false`. |
| `next_cursor` | Send it back as `cursor` to get the next page. `null` on the last page, and on a root that pages by `page` only (see below). |
| `total` | Children of the node, ignoring pagination. A lower bound when `total_capped` is `true`. |
| `total_capped` | `true` when the listing stopped counting at a cap, so more children exist than `total` says. |
| `page` | The page number you asked for. `null` on a page reached by `cursor`. |
| `start_index` | 1-based position of the page's first row, when the listing reports it. |

One root has no cursor: with no `nodeId`, a connected app whose limit names spaces, folders or files lists those items, and pages by `page` only. There, and on older servers that do not send `next_cursor`, ask for the next `page` while `has_next` is `true`.

To read a large listing to its end, follow `next_cursor`, not `page`:

- `page` numbers stop at 50. A higher `page` sent without a `cursor` returns `400`. A cursor goes on past that.
- Send the cursor exactly as you received it, with the same `nodeId` and `depth`. The cursor chooses the page and keeps the filters and order of the first page, so `page` and the date and type filters of a cursor request are ignored.
- A cursor works only for the user it was issued to, and only for the same node and sources. Any other cursor returns `400`. Start again from the first page without a `cursor`.
- When `total_capped` is `true`, show the total as a lower bound, for example "10,000+" or "at least 10,000", and stop on `has_next`, not on the total. The rendered `text` field already says "of at least N". Older servers do not send `total_capped`; their `total` may also be a lower bound, so stop on `has_next` there too.

```bash
# Print every child's name under one node, page by page.
NODE_ID="your-node-id"
CURSOR=""
PAGE=1
while :; do
  # A cursor request ignores `page`.
  RESP=$(curl -sS --fail -G "$PIPESHUB_URL/api/v1/connectors/navigate" \
    -H "Authorization: Bearer $PIPESHUB_TOKEN" \
    --data-urlencode "nodeId=$NODE_ID" \
    --data-urlencode "limit=200" \
    --data-urlencode "page=$PAGE" \
    ${CURSOR:+--data-urlencode "cursor=$CURSOR"}) || { echo "Request failed; the listing is incomplete." >&2; break; }
  echo "$RESP" | jq -r '.rows[].name'
  [ "$(echo "$RESP" | jq -r '.pagination.has_next')" = "true" ] || break
  CURSOR=$(echo "$RESP" | jq -r '.pagination.next_cursor // empty')
  # No cursor: this listing pages by number, up to page 50.
  [ -n "$CURSOR" ] || PAGE=$((PAGE + 1))
done
```

```python
import os
import requests

url = os.environ["PIPESHUB_URL"] + "/api/v1/connectors/navigate"
headers = {"Authorization": "Bearer " + os.environ["PIPESHUB_TOKEN"]}
params = {"nodeId": "your-node-id", "limit": 200, "page": 1}

while True:
    page = requests.get(url, headers=headers, params=params, timeout=60)
    page.raise_for_status()
    body = page.json()
    for row in body["rows"]:
        print(row["name"])
    pagination = body.get("pagination") or {}
    if not pagination.get("has_next"):
        break
    if pagination.get("next_cursor"):
        params["cursor"] = pagination["next_cursor"]
    else:
        # No cursor: this listing pages by number. Past page 50 the server returns 400.
        params["page"] = pagination["page"] + 1

total = pagination.get("total", 0)
print(f"{total:,}+" if pagination.get("total_capped") else f"{total:,}", "children")
```

The [MCP server's](/mcp/tools) `pipeshub_get_record_content` tool pages the same way in `mode: "navigate"`: pass the `cursor` its `Next:` line names.
