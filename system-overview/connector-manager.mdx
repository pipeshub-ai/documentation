# Connector Manager API

The Connector Manager API is how PipesHub creates, configures, signs in, turns on and deletes connectors, and how admins manage the OAuth apps that connectors sign in with. The Node.js API receives each request, checks who is calling, validates the request and forwards it to the Python connectors service, which holds the connector logic and does the work.

## Base URLs

- Connector endpoints are under `/api/v1/connectors`.
- OAuth app endpoints are under `/api/v1/oauth`.
- Health endpoints are under `/api/v1/health`.

## Connector types and connector instances

A **connector type** is a kind of source PipesHub can sync from, such as `Confluence`, `Drive` or `OneDrive`. The **registry** lists the types and the setup form each one needs.

A **connector instance** (usually just "connector") is one configured copy of a type. An organization can have several instances of the same type. Every instance has its own ID, the `connectorId`, which the instance endpoints take in the path. A `connectorId` is 1 to 64 letters, digits, underscores or hyphens; anything else is refused with `400`.

Each instance has a **scope**:

- `team`: set up by an admin for the whole organization. Every member sees team connectors in the connector lists.
- `personal`: set up by one person for their own data. Only that person sees it.

An instance moves through these states, which the responses report as fields:

| Field | Meaning |
|-------|---------|
| `isConfigured` | Its settings have been saved. |
| `isAuthenticated` | Its OAuth sign-in has completed. |
| `isActive` | Syncing is turned on. |
| `isAgentActive` | Agent use is turned on, for connectors that support agents. |
| `isLocked` | A sync or another operation is running, so changes are refused for now (see [Locked connectors](#locked-connectors)). |
| `status` | `SYNCING`, `FULL_SYNCING`, `DELETING` and so on, when something is in progress. |

## Authentication

Every endpoint except the health checks needs a bearer token:

```http
Authorization: Bearer YOUR_TOKEN
```

The token can be a signed-in session token, an OAuth access token or a personal access token. OAuth access tokens and personal access tokens must also carry at least one of the scopes listed for the endpoint (for example `connector:read`); without one, the request is refused with `403`. Session tokens are not checked for scopes.

| Scope | Allows |
|-------|--------|
| `connector:read` | Reading connectors, the registry, filters and OAuth apps |
| `connector:write` | Creating and changing connectors and OAuth apps, and OAuth sign-in |
| `connector:sync` | Turning sync on and off, stopping a sync, reindexing, and the vector store jobs |
| `connector:delete` | Deleting connectors and OAuth apps |
| `kb:read`, `kb:write` | Accepted instead of the `connector:*` scope on a few endpoints: `kb:read` for stats, navigate and lookup, `kb:write` for reindex and resync |

## Who can do what

The connectors service decides access from the caller's role in the organization. A refusal for lack of permission is `403`. A connector the caller may not see at all is reported as `404`, so the API doesn't confirm that it exists.

| Action | Team connector | Personal connector |
|--------|----------------|--------------------|
| See it in the connector lists | Every member | Its creator |
| Read it, its configuration or filters | An admin (or its creator) | Its creator only. An admin gets `404`. |
| Read its stats | An admin (or its creator). Anyone else gets `403`. | Its creator only. Anyone else, an admin included, gets `403`. |
| Create it | An admin | Anyone |
| Change its configuration, name or filters, sign it in, turn it on or off | An admin | Its creator only |
| Delete it | An admin or its creator. Anyone else gets `404`. | Its creator or an admin. Anyone else gets `404`. |
| Create, update or delete an OAuth app | An admin | An admin |
| Start a vector store cleanup or reindex | An admin | An admin |

Only its creator can read a personal connector's configuration, because the configuration carries the creator's credentials.

When beta connectors are turned off in the platform settings, the registry leaves beta connector types out, and requests for a beta connector are refused with `403`. Enterprise and business accounts also can't create a beta connector with team scope (`403`).

### Locked connectors

While a sync or another operation runs, a connector is locked. Requests that change it (configuration, name, filters, toggle, reindex, resync and delete) are refused with `409 Conflict` until the sync finishes. The message says what is running, for example "A sync is already in progress. Please wait and try again."

To end a sync early instead of waiting, call `POST /:connectorId/sync/stop` (under Sync and indexing below). It is allowed while the connector is locked, and it also clears a lock or a syncing status left behind when no sync is running.

<Accordion title="Configuration">
A connector's configuration has three sections: `auth` (how it signs in), `sync` (when it syncs) and `filters` (what it syncs and indexes). It is stored encrypted. Reading it leaves out the `credentials` and `oauth` sections, which hold the sign-in tokens.

Secrets in `auth` never come back in plain text. A secret is any field the connector type's setup form marks secret, such as an API token, a password or a client secret. The private key of an older Google Workspace connector's service account counts too. Each secret that is set comes back as `••••••••`, both when you read the configuration and in the answer to every save. A secret that isn't set comes back empty.

When you save, a secret sent as `••••••••` keeps the stored value. So you can send back the configuration you read without retyping its secrets. To change a secret, send the new value. Leaving a secret out also keeps the stored value.

## Deleting a connector

Deleting a connector is permanent. Its records don't go to the trash, even when the trash is turned on, and they can't be restored.

1. The request is checked: the caller must be the creator or an admin, no deletion may already be running, no sync may be running, and no agent may use the connector as a knowledge source.
2. The connector is marked `DELETING` before any event is published, so a deletion that finishes quickly can't race the request that started it.
3. An `appDisabled` event stops any running sync, and a `<type>.delete` event (for example `confluence.delete`) starts the deletion. If that event can't be published, the `DELETING` mark is cleared, nothing is deleted, and the request fails.
4. The request answers `202 Accepted`. The connectors service then deletes, in the background, the connector and its records, record groups, permissions and relations from the graph database; asks the indexing service to remove its embeddings; deletes its stored configuration and credentials; and deletes its stored files, keeping any content another connector still uses.
5. If the deletion fails, the `DELETING` mark is cleared and the connector's sync setting is put back to what it was, so the connector can be deleted again.

## Events

The connector endpoints publish these events on the message broker (Kafka or Redis Streams):

| Topic | Event type | Sent when |
|-------|------------|-----------|
| `entity-events` | `appEnabled` | Sync is turned on |
| `entity-events` | `appDisabled` | Sync is turned off, or a deletion starts |
| `sync-events` | `<type>.resync` | A resync is requested |
| `sync-events` | `<type>.reindex` | A reindex is requested |
| `sync-events` | `<type>.delete` | A deletion starts |

`<type>` is the connector type in lowercase with spaces removed, for example `confluence` or `onedrive`.

## Where connector data is kept

- **Connector instances** are nodes in the graph database (Neo4j or ArangoDB).
- **Configuration and credentials** are in the key-value store (Redis or etcd) at `/services/connectors/{connectorId}/config`, encrypted with AES-256-GCM. OAuth apps are stored there too, per connector type.
- **Sync schedules** are jobs in the crawling manager's queue. See the [Crawling Manager API](/system-overview/crawling-manager).

## Error Handling

Most errors share this shape. Three answers differ:

- [Local FS refusals](#local-fs-refusals) put `code` and `details` at the top level.
- A failed OAuth callback answers `200` with `success: false` and a top-level `error` string.
- A resync that can't be queued answers `200` with `resyncConnectorResponse` set to `{ "success": false, "error": "..." }`.

```json
{
  "error": {
    "code": "FORBIDDEN",
    "message": "Only the creator or an administrator can toggle this connector",
    "requestId": "req-1234"
  }
}
```

A request that fails validation has the code `VALIDATION_ERROR` and status `400`. A refusal from the connectors service keeps its own message, and its status is passed on: `400`, `401`, `403`, `404`, `409`, `422` and `429` as they are. A server failure in the connectors service becomes `500` with a plain message naming what failed, without internal details.

**Common HTTP Status Codes:**
- `200` - Success
- `202` - Accepted: a deletion or vector store job has started
- `400` - Bad request: a missing or invalid field, or a change the connector's state doesn't allow
- `401` - Missing or invalid token
- `403` - Not allowed: permission, beta connectors turned off, or a missing token scope
- `404` - The connector, type or OAuth app doesn't exist, or the caller may not see it
- `409` - Conflict: the connector is locked, already being deleted, or in use by an agent
- `500` - Server failure
- `503` - PipesHub couldn't reach the connectors service: "PipesHub is having trouble reaching one of its services. Try again in a minute; if it continues, ask your admin to check the services page."

When the connectors service can't be reached, the request is tried up to three times, with a growing wait between tries, before it fails.

### Local FS refusals

A Local FS connector syncs a folder on one desktop device. When a sync can't start because of that device, the answer is `409` with a code to branch on:

```json
{
  "success": false,
  "code": "DESKTOP_OFFLINE",
  "message": "...",
  "details": {
    "code": "DESKTOP_OFFLINE",
    "connectorId": "3f1c9a52-7d0e-4b8a-9c1e-2a6b5d4e7f80",
    "retryable": true,
    "ownerDeviceName": "Work laptop"
  }
}
```

- `DESKTOP_OFFLINE` - The owner device isn't connected.
- `DESKTOP_UNCLAIMED` - No device owns the connector yet. Turn sync on from the PipesHub desktop app on the device that has the folder.
- `DESKTOP_OWNED_BY_OTHER_DEVICE` - Another device owns the connector; `ownerDeviceName` names it.
