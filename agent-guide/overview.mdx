## What agents are

Agents are customizable AI assistants that can interact with your connected applications, search collections, and perform actions on your behalf. Unlike the standard chatbot assistant, agents are purpose-built for specific workflows and can be configured with:

- **Models**: Choose the AI model that powers your agent, or leave it empty to use your organization's default model
- **Actions**: Connect to external services like Slack, Jira, Confluence, and more
- **MCP servers**: Give the agent tools from MCP servers your organization has set up
- **Skills**: Attach skills the agent can invoke
- **API actions**: Use API actions that were created from an OpenAPI spec
- **Knowledge sources**: Access indexed documents and collections
- **Custom system prompts**: Define the agent's personality and behavior

<Note>
  **When you want to use both Connector and Action:** In the Agent Builder add nodes from **Knowledge** (Collections, API Apps) for document search and context retrieval, and add nodes from **Tools** for performing actions. Connect both to your Agent node so the agent can search context and take action in the same conversation.
</Note>

## Key Concepts

### Visual Flow Builder

Agents are built using a visual drag-and-drop flow builder powered by ReactFlow. You create agents by:

1. Starting from the **Agent** node (labeled **Core** and **Orchestrator** on the canvas), which defines the agent's basic configuration
2. Connecting **Model** nodes to power the agent's intelligence (optional; without one the agent uses your organization's default model)
3. Adding action nodes to give the agent access to external applications
4. Adding **MCP servers**, **Skills** and **API actions** nodes where you need them
5. Connecting **Knowledge** nodes (apps and collections) for indexed document search
6. Connecting the chat **Input** and **Response** handles to the chat input and chat output nodes

### Agent node

The Agent node is the central configuration for your agent. Its sections are Model, Knowledge, Toolsets (the builder still uses that label for actions), Skills, MCP servers, Input and Response.

| Field | Description |
|-------|-------------|
| **Name** | Display name for your agent (entered in the header) |
| **System prompt** | Instructions that define the agent's behavior and personality |
| **Instructions** | Detailed instructions for the agent's behavior and capabilities |
| **Starting message** | Initial greeting when users start a conversation |
| **Default reasoning effort** | Fallback reasoning effort used when the user does not choose one in chat ([Using chat](/using-chat)). Shown only when a connected model supports reasoning |
| **Send user & organization context** | When off, the agent does not receive the user's name, email or organization in its system prompt |

### Service agents

When you create an agent you choose its type. A **user agent** is a personal agent where each person signs in to the actions. A **service agent** is shared with your whole organization and uses agent-level action credentials; set them with the key icon in the palette. A service agent searches knowledge with its creator's access (or a service account an administrator grants), so everyone who uses it sees results from what that identity can read. An existing agent can be converted with **Convert to service agent**; this cannot be undone.

### Actions

Actions are collections of tools that allow agents to interact with external applications. Each action provides specific actions:

- **Jira action**: Create issues, search tickets, add comments, etc.
- **Slack action**: Send messages, search channels, manage conversations, etc.
- **Confluence action**: Create/update pages, search content, etc.
- **Gmail action**: Send emails, read messages, search, etc.
- **Calendar action**: Create events, update events, check availability, etc.
- **Drive action**: List files, manage folders, search documents, etc.

<Info>
  Actions must be configured and authenticated before they can be used in agents. See [Actions Overview](/toolsets/overview) for setup instructions.
</Info>

### MCP servers, skills and API actions

The palette also lists **MCP servers**, **Skills** and **API actions** (the last under Tools).

- [Skills](/agent-guide/skills): reusable instructions you create or import under **Workspace → Your skills**.
- [MCP servers](/agent-guide/mcp-servers): tools from MCP servers an admin adds under **Workspace → MCP servers**, or that you add under **Workspace → Your MCP servers**.
- [API actions](/agent-guide/api-actions): operations from an OpenAPI spec, which an admin adds under **Workspace → Actions**.

### Collections

Agents can access your indexed knowledge sources:

- **Connectors**: Data synced and indexed from connected applications for querying and search (Google Drive, SharePoint, etc.)
- **Collections**: Custom document collections you've uploaded

## Agent Capabilities

### What Agents Can Do

| Capability | Description |
|------------|-------------|
| **Search Knowledge** | Query indexed documents and return relevant information |
| **Perform Actions** | Create tickets, send messages, update pages via actions |
| **Multi-tool Workflows** | Combine multiple actions in a single conversation |
| **Context-Aware Responses** | Use system prompts to maintain consistent behavior |

## Frequently Asked Questions

<AccordionGroup>

<Accordion title="What's the difference between Connectors and Actions?">

| Aspect | Connectors | Actions |
|--------|-----------|----------|
| **Purpose** | Sync and index data for search | Enable agents to perform actions |
| **Data Flow** | One-way (import data into PipesHub) | Two-way (read and write via API) |
| **When to Use** | Query/search data | Perform actions on data |

**Example:** Use a **Gmail Connector** to index and search your email history. Use a **Gmail action** to send new emails through an agent.

</Accordion>

<Accordion title="When should I use a Connector vs an Action?">

**Connector**: use when you need document context search. Connectors sync and index your documents, emails, and pages so your assistant can find and use that context.

**Action**: use when the agent needs to do something in another app: create or update content, send messages, or run analytical queries (e.g. JQL, CQL, reports).

**Quick takeaway:** Search & context → **Connector**. Do something in another app → **Action**.

</Accordion>

<Accordion title="Can I use one OAuth app for both Connector and Action?">

Yes! You can create a single OAuth app in the service's developer console and use it for both:

**What you need to add in your OAuth app:**

1. **Both redirect URLs:**
   - Connector callback URL (e.g., `/connectors/oauth/callback/Gmail`)
   - Action callback URL (e.g., `/api/oauth/callback/Gmail`)

2. **Both scope types:**
   - Read-only scopes for the Connector (to index data)
   - Read/write/delete scopes for the action (so the agent can make changes)

**Benefits:**
- Simpler setup - One OAuth app instead of two
- Same Client ID and Client Secret for both configurations
- Easier management in the service's developer console

</Accordion>

<Accordion title="How do I know which nodes to connect in Agent Builder?">

Follow this pattern:

1. **Agent** node (required) - The center of your agent
2. **Model** (optional) - Connect an AI model, or the agent uses your organization's default
3. **Action nodes** (optional) - For actions like sending emails, creating tickets
4. **MCP servers, Skills and API actions** (optional) - For extra tools and reusable instructions
5. **Knowledge nodes** (optional) - For searching indexed data from Connectors and collections
6. **Chat input and chat output**: Connect them to the Input and Response handles

All nodes must connect through the Agent node. The agent will have access to all connected actions and knowledge sources.

</Accordion>

<Accordion title="Can I choose what knowledge source or tool the agent uses during chat?">

Yes! While chatting with an agent, you can select:

- **Specific Collections**: Query data from particular Connectors (e.g., search only Confluence or only Drive)
- **Specific Actions**: Use particular tools (e.g., send via Gmail or create Jira ticket)
- **Model**: Choose which AI model to use for the query

This gives you control at any time during the conversation to specify where the agent should search or which action to perform. See [Using chat](/using-chat).

</Accordion>

<Accordion title="Can I connect multiple Models to one agent?">

Yes! You can connect multiple Model nodes to the Agent node. 

When chatting with the agent, users can select which model to use for specific queries from the chat interface. This allows:

- Using different models for different complexity levels
- Flexibility to choose the best model for each task

</Accordion>

</AccordionGroup>
