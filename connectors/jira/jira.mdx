## Overview

Jira is the leading project management and issue tracking platform developed by Atlassian. It's widely used by software development teams, IT departments, and business teams to plan, track, and manage work through customizable workflows.

<Info>
  This page is for **Jira Cloud**, the version Atlassian hosts for you. If you run Jira on your own servers, use the [Jira Data Center connector](/connectors/jira/jira-data-center) instead.

  In the connector catalog, the team connector is shown as **Jira**. A separate **Jira Cloud Personal** connector syncs only what your own account can see; see [Personal connector](#personal-connector).
</Info>

### Jira Data Structure

The connector understands Jira's hierarchical data model:

**Projects → Issues → Comments/Attachments**

| Entity | Description |
|--------|-------------|
| **Projects** | Top-level containers for organizing work (e.g., Engineering, Marketing) |
| **Issues** | Work items including bugs, tasks, stories, epics, and custom types |
| **Comments** | Discussion threads attached to issues |
| **Attachments** | Files, images, and documents attached to issues |
| **Users & Groups** | Team members and their group memberships |
| **Project Roles** | Role-based access control for project permissions |
| **Application Roles** | Licensed application groups used in permission schemes |

### What Gets Synced

The connector indexes the following content for AI-powered search:

- **Issue Content**: Summary, description (with rich text/ADF support), status, priority, labels
- **Issue Metadata**: Reporter, assignee, created/updated dates, custom fields
- **Comments**: Comments that everyone who can see the issue can read, with author information. Comments restricted to a role or group, and Jira Service Management internal notes, are not indexed.
- **Attachments**: All file types attached to issues (PDFs, images, documents), except files attached only in a restricted comment or internal note
- **Permissions**: Project-level and issue-level access controls are preserved

## Configuration Guide

The Jira connector supports **two authentication methods**. Both sync the same data — pick whichever fits your rollout.

### Email visibility (recommended)

PipesHub matches Jira users to PipesHub accounts by email address. This applies to **both** authentication methods (OAuth and API Token).

<Info>
  If a user hides their email in Jira, PipesHub can still match them, as long as that user already exists in PipesHub or in another connected source. Making emails visible is not required. It only makes the first sync faster, because the connector does not have to look up each user one by one.
</Info>

**How to configure email visibility.** To make the first sync faster, each user can complete these steps in their Atlassian account:

1. Click your **profile picture** in the top right → select **Account Settings**.

    alt="Access User Profile Settings"
    className="block mx-auto w-11/12"
  />
</div>

2. Select the **Profile and visibility** tab.
3. Scroll down to the **Contact** section.
4. In the **Who can see this?** dropdown for your email address, select either **Anyone** (recommended) or **Your organization**.

<div className="text-center">
  <img
    src="/images/connectors/jira/email_visibility_setting.png"
    alt="Set Email Visibility to Organization"
    className="block mx-auto w-11/12"

With **Only you and admins**, the connector can't read your email from Jira and has to find you through PipesHub or another connected source instead.

📖 **Official documentation:** [Update your profile and visibility settings](https://support.atlassian.com/atlassian-account/docs/update-your-profile-and-visibility-settings/)

<Info>
  This is a **per-user setting** that each user configures. Administrators cannot change this setting for other users.
</Info>

### Required privileges

The connector reads a few admin-only Jira APIs to work out who is allowed to see what. Use an account with the **Administer Jira** global permission: the user who authorizes OAuth, or the owner of the API token. Without it the sync still runs, but some access is missing.

| What the connector reads | Needs | What happens if access is denied |
|--------------------------|-------|----------------------------------|
| Audit log | Administer Jira | Deleted issues are not found through the audit log and may stay in PipesHub. See [Troubleshooting](#troubleshooting). |
| Application roles | Administer Jira | Projects that grant access through an application role give access only to the person who set up the connector. |
| Issue security schemes and who holds each level | Administer Jira | Issues that have a security level are not shown to anyone in PipesHub until the account can read them. |

<Note>
  This applies to the team connector only. The [Jira Cloud Personal connector](#personal-connector) doesn't read these APIs.
</Note>

### Choose an authentication method

| Method | Best for |
|--------|----------|
| **OAuth 2.0 (3LO)** | Org-wide rollouts, production — one admin authorizes, and refresh tokens rotate automatically. Requires Atlassian Developer Console access. |
| **API Token** | Single-account setups, quick POCs, or environments where you cannot register an OAuth app. Fastest path to sync. |

Available sync filters:

1. **Project Keys** — Filter by Jira projects.
   - Operator: `In` (include only) or `Not In` (exclude)
   - Selection: searchable dropdown of all your Jira projects (shows names + keys, e.g., "Engineering (ENG)")
2. **Modified Date** — Filter by last modification date. Operators: `Is After`, `Is Before`, `Is Between`.
3. **Created Date** — Filter by creation date. Same operators.

<Info>
  The project list is dynamically fetched from your Jira workspace. Type to search and filter; select multiple projects as needed.
</Info>

**Indexing filters** — control what synced data gets processed for AI search. All data is synced, but only enabled content types are indexed.

- **Enable Manual Indexing** (default: off) — when on, synced issues are not indexed until you pick them; when off, everything synced is indexed
- **Index Issues** (default: enabled) — include issue content (description + comments) in search
- **Index Issue and comment Attachments** (default: enabled) — include attachments in search

<Info>
  Comments are stored as part of the issue content (not as separate records). When **Index Issues** is enabled, both issue descriptions and comments are indexed together.
</Info>

**Example configurations:**

- *Sync only Engineering project:* Project Keys → Operator `In` → select "Engineering"
- *Exclude archived projects:* Project Keys → Operator `Not In` → select archived projects
- *Recent issues only:* Modified Date → Operator `Is After` → Date `2024-06-01`
- *Index issues but not attachments:* disable the **Index Issue and comment Attachments** toggle

Click **Save** to save your configuration. PipesHub confirms the instance is ready with a final dialog — **"Instance is configured and ready to sync!"** — offering two choices: **I'll do it later** or **Start syncing now**.

## Personal connector

**Jira Cloud Personal** is a separate connector that syncs Jira Cloud issues your own account can see into your personal workspace. Set it up under Workspace Settings → **Personal** → **Your Connectors**.

<div className="text-center">
  <img
    src="/images/connectors/jira/ph-jira-cloud-personal-setup.png"
    alt="Set up Jira Cloud Personal: Authenticate tab"
    className="block mx-auto w-2/3"
  />
</div>

- **What it syncs:** only the projects and issues visible to the credentials you provide.
- **Who can see it:** only you, the user who created the connector. It doesn't read Jira permission schemes, groups, other users, or the audit log, so it doesn't need Jira admin rights.
- **Sign-in:** OAuth 2.0 or API Token, with the same fields as the team connector. For OAuth, the Redirect/Callback URL ends in `connectors/oauth/callback/JiraCloudPersonal`, and the app needs fewer scopes:

| Scope | API |
|-------|-----|
| `read:jira-work` | Jira API (classic) |
| `read:jira-user` | Jira API (classic) |
| `read:user:jira` | Jira API (granular) |
| `read:avatar:jira` | Jira API (granular) |
| `read:account` | User identity API |

PipesHub also requests `offline_access` for you. The **Configure records** tab has the same sync settings, filters, and indexing options as the team connector. Deleted issues are found by comparison on every sync; see [Connector Workflow](#connector-workflow).

## Supported Features

The Jira connector syncs the following data from your Jira Cloud workspace:

- **Projects** — all accessible projects with their configurations and permission schemes
- **Issues** — full issue content including summary, description, status, priority, and custom fields
- **Comments** — comments that everyone who can see the issue can read, with author information. Comments restricted to a role or group, Jira Service Management internal notes, and files attached only in them are not indexed.
- **Attachments** — files attached to issues (images, documents, etc.)
- **Users** — user profiles and account information
- **Groups** — user groups and memberships
- **Project Roles** — role assignments for project access control
- **Permissions** — project permissions and issue-level access controls

## Troubleshooting

<AccordionGroup>

<Accordion title="Troubleshooting" icon="circle-exclamation">

### Common issues

**Invalid client credentials error (OAuth):**
- Verify Client ID and Client Secret are correct — no extra spaces
- Check that the OAuth app is active in Atlassian Developer Console
- Regenerate the secret if necessary and update PipesHub

**Callback URL mismatch error (OAuth):**
- Ensure the Redirect/Callback URL in PipesHub exactly matches the Callback URL in Atlassian
- Check for trailing slashes, protocol differences (`http` vs `https`), or casing
- Update both configurations to use the same URL

**API token authentication fails:**
- Confirm the token was copied correctly — no leading/trailing whitespace
- The token may have been revoked or expired; create a new one at [id.atlassian.com/manage-profile/security/api-tokens](https://id.atlassian.com/manage-profile/security/api-tokens)
- Verify the **Email** field matches the Atlassian account that created the token
- Make sure the token was created with **Create API token**, not **Create API token with scopes**
- Verify the **Base URL** matches your Jira site (must include `https://` and match `*.atlassian.net`)

**Base URL format issues (API Token):**
- Must include the protocol: `https://`
- Use the site root, such as `https://acme.atlassian.net`. A trailing slash is removed automatically
- Must match the actual Jira Cloud site (usually `*.atlassian.net`)
- Do not include paths like `/jira` or `/browse/...`

**Authorization failed (OAuth):**
- Verify you're signing in with an account that has Jira access
- Ensure your Jira site is selected during authorization
- Check that all required API scopes are configured

**No data syncing:**
- Verify the connector status shows **Active**
- Check that the authenticating user (OAuth) or token-owning user (API Token) has access to Jira projects
- Ensure projects are not restricted or archived
- Review sync logs for specific error messages

**Token expired or sync stopped:**
- If an OAuth connector doesn't sync for 90 days, Atlassian expires its refresh token; use **Reauthenticate** to sign in again
- API tokens expire after at most one year and can be revoked from the Atlassian account page; generate a new one and update the **Authenticate** tab
- Check if the OAuth app is still active in Developer Console

**Permission denied for specific issues:**
- Verify the authenticating user has read access to the issues
- Check project permissions in Jira
- Review issue security schemes that may limit access

**Deleted issues still appear in PipesHub:**
- PipesHub usually finds deleted issues through Jira's audit log. Jira provides that log only when at least one Jira product on the site is on a paid plan, and only to an account allowed to read it.
- **Free plan:** if every Jira product on your site is on a Free plan, the connector sends one notice, "finds deleted issues more slowly on Jira's Free plan". No action is needed. Each sync compares the issues in each synced project with the ones PipesHub holds and removes those Jira no longer has. This takes more requests than the audit log, so syncs of large projects can take a little longer. If Jira's issue list can't be read in full, nothing is removed and the next sync tries again.
- **Missing permission:** if the notice says the connector "is missing the audit log permission", ask a Jira admin to give the connector's account the **Administer Jira** global permission (under **Settings → System → Global permissions**), which reading the audit log requires.
- **Jira Cloud Personal connector:** it doesn't use the audit log. Each sync compares the issues in each synced project with the ones PipesHub holds, so a deleted issue is removed on the next sync that reads the project's issue list in full. If the issue is still there, run the sync again and check that the project synced without errors. See **Deletion detection** under [Connector Workflow](#connector-workflow).

**Issues or a project disappeared from the Jira Cloud Personal connector:**
- The connector keeps only what your Jira account can see. If you lose access to an issue or a project (for example, through a permission change or an issue security level), PipesHub removes it on the next sync, as if it had been deleted.
- Ask a Jira admin to restore your access. A project you can see again is synced in full on the next sync. A single issue comes back the next time it changes in Jira, or after a full resync.

**Missing comments or attachments:**
- Verify indexing filters are enabled for issues and attachments
- Check that the user has permission to view comments/attachments
- Comments restricted to a role or group, Jira Service Management internal notes, and files attached only in them are not indexed
- Images up to 5 MiB are embedded in the issue content; larger images and other files are stored as separate file records under the issue

<Warning>
  If you modify OAuth application settings in Atlassian Developer Console (Client ID, Secret, Callback URL, or scopes), update the configuration in PipesHub and re-authorize. For API tokens, re-enter the token in the **Authenticate** tab if you regenerate it.
</Warning>

## Connector Workflow

<AccordionGroup>

<Accordion title="Synchronization Process" icon="sync">

The Jira connector follows a structured synchronization process to ensure all data is accurately synced and permissions are properly maintained.

### Sync overview

Each sync runs these steps in order:

| Step | Data Synced | Purpose |
|------|-------------|---------|
| 1 | Users | Sync Jira users with their profiles |
| 2 | Application roles | Map application roles to their groups, and keep only users with a Jira license |
| 3 | Groups | Sync groups and user-group memberships |
| 4 | Projects | Fetch projects (filtered if configured) |
| 5 | Project roles | Sync project role assignments |
| 6 | Project lead roles | Assign project lead permissions |
| 7 | Issues | Sync issues, comments, and attachments |
| 8 | Deletions | Detect and remove deleted issues |
| 9 | Removed projects | Remove projects that are no longer synced |

### Full sync vs incremental sync

The connector automatically determines whether to perform a full or incremental sync:

**Full sync** occurs when:
- First-time synchronization (no sync checkpoint exists)
- Sync filters have been modified since last sync
- Manual full sync is triggered

**Incremental sync** occurs when:
- A valid sync checkpoint exists
- Filters haven't changed
- Asks Jira only for issues updated since the last checkpoint, with a small overlap so issues Jira indexed late are not missed

### User & group synchronization

1. **User fetch** — retrieves all users from Jira with their account IDs, emails, and display names
2. **Group sync** — fetches all groups and their member lists
3. **Membership mapping** — creates user-to-group relationships for permission resolution

If a group's member list or a project's permission scheme can't be read for a temporary reason (rate limiting after retries, a server error, a network failure), the group or project keeps the access PipesHub already has, and the project's issues still sync. Project roles that include that group are left as stored too. A group that no longer exists in Jira ends up empty, as before.

### Project synchronization

1. **Project fetch** — retrieves projects (filtered by project keys if configured)
2. **Permission scheme** — extracts project permission schemes for access control
3. **Role assignment** — syncs project-specific roles (Admin, Developer, Viewer, etc.)
4. **Lead roles** — assigns project lead permissions to designated users

### Issue synchronization

For each project, the connector:

1. **Builds JQL query** — constructs query with date filters and project scope
2. **Batched fetching** — retrieves issues in batches (default: 100 per request)
3. **Content processing** — parses issue description (ADF format → Markdown with embedded images); extracts metadata (status, priority, labels, etc.)
4. **BlockGroup structure** — creates hierarchical content structure:
   - **Description BlockGroup** (index=0): contains issue description with inline attachments
   - **Comment Thread BlockGroups**: each thread gets its own BlockGroup with `parent_index=0`
   - **Comment Blocks**: individual comments stored as Blocks within their thread BlockGroup
5. **Attachment processing** — maps attachments to their correct location (description or specific comments)
6. **Permission assignment** — applies project and issue-level permissions

<Note>
  Comments are stored as **Blocks** within the issue's BlocksContainer (not as separate records). This enables efficient threaded comment organization and ensures comments are deleted automatically when the parent issue is removed.
</Note>

### Deletion detection

The connector uses Jira's **Audit Log API** to detect deleted issues:

1. Queries audit log for `ISSUE_DELETE` events since last sync
2. Identifies deleted issue keys from audit records
3. Removes issue records from the index
4. Comments are automatically deleted with the issue (stored as Blocks within the issue)

<Note>
  **On Jira's Free plan.** Jira provides the audit log only when at least one Jira product on the site is on a paid plan. When every Jira product is on a Free plan, the connector instead lists the issue IDs in each synced project on every sync and compares them with the issues PipesHub holds. An issue missing from the list is removed only after Jira confirms it no longer exists, or no longer lets the connector's account see it. If the list can't be read in full, nothing is removed and the next sync tries again. An issue your date filters leave out isn't removed by this check while it still exists in Jira. The connector sends one notification saying it works this way; see [Troubleshooting](#troubleshooting).
</Note>

#### Jira Cloud Personal connector

The **Jira Cloud Personal** connector syncs what your own Jira account can see. A personal account can't read the audit log, so this connector never asks for it and finds deleted issues by comparison on every sync instead:

1. For each synced project, it lists the issue IDs Jira shows your account and compares them with the issues PipesHub holds
2. It asks Jira once more about each issue missing from the list
3. It removes the issue and its attachments only when Jira answers that the issue no longer exists, or that your account can no longer see it

The listing takes about one request per 5,000 issues in a project, plus one request per missing issue. An issue your date filters leave out isn't removed by this check while it still exists in Jira.

**When Jira can't be read.** If a project's list can't be read to the end, nothing is removed for that project and the next sync tries again.

**When you lose access.** Jira answers the same way for a deleted issue and for one your account can no longer see, so both are removed from PipesHub. An issue you can see again comes back the next time it changes in Jira, or after a full resync.

**When a whole project leaves your view.** A synced project can drop out of the projects Jira shows your account because it was deleted or archived, or because you lost access. PipesHub then asks Jira about the project. If Jira confirms it is gone or hidden, PipesHub checks each of its issues, removes the ones Jira confirms, and removes the project once it is empty. A project that comes back into view is synced in full again. PipesHub doesn't touch a project you left out with the **Project Keys** filter, or one Jira still answers for.

**When the sign-in stops working.** Before removing anything, the connector checks that Jira still recognises your account. If the token has expired or been revoked, nothing is removed until you reconnect.

### Checkpoint management

After each successful sync:
- Stores the latest issue update timestamp as checkpoint
- Records current filter configuration to detect changes
- Per-project checkpoints enable resumable syncs on failures

## FAQ

<AccordionGroup>

<Accordion title="Which authentication method should I choose?">

| | OAuth 2.0 | API Token |
|---|-----------|-----------|
| **Best for** | Org-wide rollouts, production | Single-account setups, quick POCs |
| **Credentials model** | One admin authorizes; refresh tokens rotate automatically | Single token that expires after at most one year |
| **Prerequisites** | Atlassian Developer Console admin access | Any Atlassian account |

Choose **OAuth** for production. Choose **API Token** when you cannot register a developer-console app or just want to get syncing quickly. Both methods sync the same data.

</Accordion>

<Accordion title="What's the difference between Jira Connector and Jira Toolset?">

| Aspect | Jira Connector | Jira Toolset |
|--------|----------------|--------------|
| **Purpose** | Sync and index Jira data for search | Enable agents to perform actions in Jira |
| **Data Flow** | One-way (import data into PipesHub) | Two-way (read and write via API) |
| **When to Use** | Query/search issues, projects, comments | Create issues, update tickets, add comments |

**Example:** Use **Jira Connector** to search and retrieve existing ticket information. Use **Jira Toolset** to let agents create new issues or update ticket status.

</Accordion>

<Accordion title="Queries not returning results. What could be wrong?">

Check these in order:

1. **PipesHub email mismatch** — the email used to authenticate the Jira connector must match your PipesHub account email. For OAuth, this is the email you signed in with during consent; for API Token, it's the **Email** field on the **Authenticate** tab.
   - **Fix:** reconfigure the connector and authenticate using the same email as your PipesHub account.

2. **Hidden email** — if your Atlassian email visibility is set to *Only you and admins*, PipesHub matches you only if you already exist in PipesHub or in another connected source.
   - **Fix:** set it to **Anyone** or **Your organization** (see [Email visibility](#email-visibility-recommended) above), then run a sync.

3. **Verify in All Records** — go to **All Records** in PipesHub and confirm the Jira issues you expect are actually present. If they're missing, the sync hasn't reached them yet — check sync status in **Settings → Connectors**.

</Accordion>

<Accordion title="Is it possible to index only specific Jira projects?">

Yes. On the **Configure records** tab, use the **Project Keys** filter with the `In` operator and pick the projects you want to include. Or use `Not In` to exclude specific projects.

</Accordion>
