PostgreSQL can hold all of PipesHub's data in one database. This setup is for **standalone installs and new slim deployments**. **Every PostgreSQL option is off by default**, so an install is unchanged until you set the variables below.

<Note>
  An existing deployment keeps the stores it runs today. A full deployment uses Redis (message broker, configuration, job scheduling and cache), Qdrant for vectors and Neo4j for the graph. Use the settings on this page when you set up a new standalone or slim install.
</Note>

## What PostgreSQL can replace

| Data | Variable | Default | PostgreSQL value |
|---|---|---|---|
| Documents (users, orgs, chats, files metadata, OAuth) | `DOC_STORE` | `mongo` | `postgres` |
| Configuration and credentials | `KV_STORE_TYPE` | `redis` | `postgres` |
| Message broker | `MESSAGE_BROKER` | `redis` | `postgres` |
| Crawl and sync scheduler | `CRAWL_SCHEDULER` | BullMQ when Redis is configured | `postgres` |
| State shared across processes (leader keys, leases, retry counters, the Node API cache) | `REDIS_MODE` | `standalone` | `postgres` |
| Vectors | `VECTOR_DB_TYPE` | `qdrant` | `pgvector` |
| Knowledge graph | `DATA_STORE` | `neo4j` in `env.template` (`arangodb` if unset) | `postgres` |

`PIPESHUB_STORE=postgres` is a shortcut for four of these. It sets `KV_STORE_TYPE`, `MESSAGE_BROKER`, `CRAWL_SCHEDULER` and `REDIS_MODE` to `postgres` for any of them you have not set. A value you set always wins, so remove or comment out the `KV_STORE_TYPE=redis` and `MESSAGE_BROKER=redis` lines in your `.env` first. It does not change `DOC_STORE`, `VECTOR_DB_TYPE` or `DATA_STORE`.

You can switch each store on its own. For example, you can keep Kafka for messages and use PostgreSQL for configuration.

## Before you start

You need:

- A PostgreSQL server you control, with pgvector 0.7.0 or later. You need it even if you keep Qdrant for vectors, because the schema always includes the vector tables. The stock `postgres` image does not include pgvector.
- An administrator login to create roles, and the database prepared with the steps below.

<Steps>
  <Step title="Create the roles">
    Run from the `backend` directory of the repository. This creates the roles and installs the extensions into schema `ext`:

    ```bash
    PG_ADMIN_URL=postgresql://admin:...@db-host:5432/pipeshub \
    PG_BOOTSTRAP_EXTENSIONS=vector,pg_trgm \
    python -m db.bootstrap_roles
    ```

    Also set a password for every login the run creates: `PG_NODE_PASSWORD`, `PG_CONNECTORS_PASSWORD`, `PG_INDEXING_PASSWORD`, `PG_QUERY_PASSWORD`, `PG_KV_PASSWORD`, `PG_MIGRATE_PASSWORD`, `PG_JOBS_PASSWORD` and `PG_BACKUP_PASSWORD`. If one is missing, the run exits with code `2` before it creates anything. Set `PG_BOOTSTRAP_ALLOW_NO_PASSWORD=1` instead if these logins use peer, trust or certificate authentication. A role that already exists is never changed, so its password is not needed.

    Keep `PG_BOOTSTRAP_EXTENSIONS=vector,pg_trgm` even if you do not use pgvector. The next step stops with an error when the `vector` extension is not installed in schema `ext`.
  </Step>
  <Step title="Apply the schema">
    ```bash
    PG_MIGRATE_URL=postgresql+psycopg://pipeshub_migrate:...@db-host:5432/pipeshub \
    python -m db.migrate
    ```

    Use a direct address to PostgreSQL, not a pooler. The same job ships as the `pipeshubai/pipeshub-migrate` image. Exit code `0` means done. Exit code `4` means the database failed a safety check. On a database that already had the schema, the run changed nothing. On a new, empty database the check runs after the schema is applied, so the schema stays in place: read the reported problems before you start PipesHub on it.
  </Step>
  <Step title="Give each service its login">
    Each process connects with its own service login:

    | Variable | Meaning |
    |---|---|
    | `PG_NODE_URL` | Login of the Node API. |
    | `PG_CORE_URL` | Login of the Python service. `PG_RUNTIME_SERVICE` names its role: `node`, `connectors`, `indexing`, `query` or `kv`. `connectors` is the default. In the all-in-one image, `PG_CORE_QUERY_URL`, `PG_CORE_INDEXING_URL` and `PG_CORE_CONNECTORS_URL` give each process its own login, also used as its `PGVECTOR_DSN`. |
    | `PG_JOBS_URL` | Jobs login. Required with `DOC_STORE=postgres`. `python -m db.maintain` needs it as a direct address. |
    | `PG_POOLER` | `pgbouncer_txn` (default), `pgbouncer_session`, `azure_pgbouncer` or `none` (a direct address). |
    | `PG_LISTEN_URL` | A direct address for `LISTEN`. Required behind a transaction pooler. With `PG_POOLER=none`, `PG_CORE_URL` is used. |

    <Warning>
      These connections carry credentials and other configuration. When PostgreSQL is not on the same host, require TLS: add `?sslmode=verify-full` (or at least `sslmode=require`) to every `PG_*_URL` and to `PGVECTOR_DSN`, and give each login a strong password.
    </Warning>

    Pool sizes and timers have defaults you can leave alone. Python services: `PG_POOL_MAX` 10, `PG_JOBS_POOL_MAX` 3, `PG_POOL_IDLE_SECONDS` 300, `PG_POOL_MIN` 1, `CONFIG_CACHE_TTL_SECONDS` 60. Node API: `PG_NODE_POOL_MAX` 10, `PG_JOBS_POOL_MAX` 2. Both: `PG_LISTEN_PING_S` 10.
  </Step>
</Steps>

## Switch a store on

Set the variable in the environment of every PipesHub process, then restart. With Docker Compose, most of these do not reach the container yet; see [Docker Compose](#docker-compose). Do these one at a time and check each (see [Check that it works](#check-that-it-works)).

### Configuration, messages and shared state

```bash
PIPESHUB_STORE=postgres
```

Or set `KV_STORE_TYPE=postgres`, `MESSAGE_BROKER=postgres` and `REDIS_MODE=postgres` yourself. With these on, PipesHub needs no Redis server. The Node API keeps its cache (sign-in sessions and e-mail rate-limit counters) in PostgreSQL, so every API process shares it and a restart does not sign users out. The Python services keep their caches in each process and drop stale entries when PostgreSQL notifies them. Without a direct address for `LISTEN` (`PG_LISTEN_URL`, or `PG_POOLER=none`), their permission caches are off.

With `MESSAGE_BROKER=postgres`:

- Delivery is ordered by message key. There are no fair-scheduling lanes, and `FAIR_SCHEDULING_LANE_COUNT` is ignored.
- Failed messages are retried with backoff and then moved to a dead-letter state.

`REDIS_MODE=inprocess` also runs without Redis, but keeps state in one process. Use it for a single process only.

### Documents

```bash
DOC_STORE=postgres
```

### Vectors (pgvector)

```bash
VECTOR_DB_TYPE=pgvector
PGVECTOR_DSN=postgresql://pipeshub_indexing_login:...@db-host:5432/pipeshub
```

Notes:

- `PGVECTOR_DSN` is the login of the process that reads it (`pipeshub_<service>_login`). Set it per process: indexing writes vectors, so it needs the indexing login, while the query login can only read. If you leave it out, the DSN under the `/services/pgvector` configuration key is used.
- The vector table needs a partition before the first vector write. A worker creates it, so run one per database: `PG_MIGRATE_URL=... PG_JOBS_URL=... python -m db.maintain placement --watch`. Without it, the first write fails after 30 seconds.
- **The embedding model cannot be changed** on a PostgreSQL vector store. Choose it before you index.

### Knowledge graph

```bash
DATA_STORE=postgres
```

The graph lives in the `graph` schema. Each process uses its `PG_CORE_URL` login. The default graph store is not changed unless you set this.

## Check that it works

- **Schema:** `python -m db.migrate` exits `0`.
- **Logs:** each service logs the store it chose at start. Look for `pgvector provider created and connected` for vectors and `Creating postgres provider (from DATA_STORE env)` for the graph. An unsupported `PIPESHUB_STORE`, `DOC_STORE`, `MESSAGE_BROKER`, `REDIS_MODE`, `VECTOR_DB_TYPE` or `DATA_STORE` value stops the service with an error that names the variable.
- **Round trip:** sign in, add a record or run a search, and confirm it works end to end.

## Docker Compose

With the shipped Compose files, only the document store can be moved to PostgreSQL today:

- The opt-in `postgres` profile starts PostgreSQL (with pgvector) and PgBouncer and creates the roles.
- From a repository checkout, `PIPESHUB_COMPOSE_OVERRIDES=docker-compose.postgres-docstore.yml ./install.sh` also runs the schema job and gives the app container `DOC_STORE=postgres`, `PG_NODE_URL` and `PG_JOBS_URL`. Use it for a new install: it does not copy data from MongoDB. See the [Compose PostgreSQL README](https://github.com/pipeshub-ai/pipeshub-ai/blob/main/deployment/docker-compose/postgres/README.md).
- The app container gets `KV_STORE_TYPE`, `MESSAGE_BROKER`, `REDIS_MODE` and `DATA_STORE` from `.env`, but not `PIPESHUB_STORE`, `CRAWL_SCHEDULER`, `VECTOR_DB_TYPE`, `PG_CORE_URL`, `PG_POOLER`, `PG_LISTEN_URL` or `PGVECTOR_DSN`. Setting those in `.env` changes nothing, and the Python services cannot reach PostgreSQL without `PG_CORE_URL`, so keep the other stores on their defaults with Compose.

There is no Helm chart option yet.
