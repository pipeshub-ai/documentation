The Node.js API keeps its documents in MongoDB unless `DOC_STORE` says otherwise: users, organizations, groups, sign-in settings, access tokens, OAuth apps, projects, conversations, notifications and file metadata. This page moves those documents into PostgreSQL on an install that already has data, and switches the API over.

The guide moves only the document store. Search vectors, the graph (records, permissions, hierarchy) and the message queue stay where they are. See [Other stores](#other-stores).

<Info>
A new install can start on PostgreSQL directly and needs none of this: `PIPESHUB_COMPOSE_OVERRIDES=docker-compose.postgres-docstore.yml ./install.sh`.
</Info>

## Choose a path

The migration tool ships in the PipesHub image as `node /app/backend/dist/scripts/docstore-migrate.js`. It can move the data in two ways:

| | Offline move | Online move |
|---|---|---|
| MongoDB | Any (the Docker Compose default is a single server) | A replica set (it follows MongoDB's change stream) |
| Downtime | The API is stopped while the data is copied and checked | Writes pause for a few minutes during the switch |
| Comparison before you switch | The tool checks every copied document | You can also run the live application in shadow mode (`DOC_STORE=shadow`) and compare real reads |
| Commands | `migrate --offline` | `migrate --online`, `follow run`, `verify --incremental`, `cutover` |

The Docker Compose install runs MongoDB as a single server, so it uses the offline move. The online move and shadow mode need MongoDB as a replica set.

Every command prints a JSON report on standard output and progress lines on standard error. It exits `0` when it succeeds, `1` when it found problems or refused, and `2` on an error. `status` shows the current job and its progress at any time.

## Prerequisites

- A checkout of the PipesHub repository at the release your install runs (the tag that matches `IMAGE_TAG` in `.env`). The schema job that builds the PostgreSQL tables is built from it.
- The PostgreSQL passwords in `.env`. Installs made with a recent `install.sh` already have them. Otherwise add these lines, each a long random value of letters, digits and `. _ ~ -` only (for example `openssl rand -hex 16`):

  ```bash
  PG_ADMIN_PASSWORD=
  PG_NODE_PASSWORD=
  PG_CONNECTORS_PASSWORD=
  PG_INDEXING_PASSWORD=
  PG_QUERY_PASSWORD=
  PG_KV_PASSWORD=
  PG_JOBS_PASSWORD=
  PG_MIGRATE_PASSWORD=
  PG_BACKUP_PASSWORD=
  ```

- Free disk for PostgreSQL of about 1.4 times the size of the MongoDB data, for indexes, text search and the write-ahead log. Preflight works out the figure from MongoDB's data size.
- For the online move: MongoDB running as a replica set, with an oplog that covers the copy, the check and a day of following. Preflight warns when the oplog window is shorter than 24 hours.

The commands below run from `deployment/docker-compose` in that checkout, with your install's `.env` copied next to `docker-compose.yml`. Set the Compose project name your install uses (`COMPOSE_PROJECT_NAME` in `.env`, or `pipeshub-ai`):

```bash
export COMPOSE_PROJECT_NAME=pipeshub-ai
```

## 1. Back up

Follow [Backup and restore](/deployment/backup-restore) and keep `.env` with the backup. The move does not change MongoDB's data, but a backup is the only way back from a mistake made by hand.

## 2. Start PostgreSQL beside the existing stores

Add the two PostgreSQL profiles to `COMPOSE_PROFILES` in `.env` (keep the profiles already there), for example:

```bash
COMPOSE_PROFILES=graph-neo4j,sandbox,postgres,postgres-migrate
```

Start PostgreSQL, its connection pooler, and the schema job:

```bash
docker compose up -d --build postgres pgbouncer pipeshub-migrate
docker compose logs pipeshub-migrate     # ends with "migrate: done"; the job exits 0
```

The application keeps running on MongoDB. Nothing connects it to PostgreSQL yet.

### Open the import login

The copy writes as its own login, `pipeshub_import`, which cannot log in until you allow it. Allow it for the length of the move, with a password of letters, digits and `. _ ~ -`. `\password` sends the server a hash, never the password itself:

```bash
docker compose exec postgres psql -U postgres -d pipeshub -c 'ALTER ROLE pipeshub_import LOGIN'
docker compose exec postgres psql -U postgres -d pipeshub -c '\password pipeshub_import'
```

### Set the tool's connections

The tool reads MongoDB's address from the application's own environment. It also needs these PostgreSQL logins, given on the command line below:

| Variable | Login |
|---|---|
| `PG_IMPORT_URL` | `postgresql://pipeshub_import:<import password>@postgres:5432/pipeshub` (direct, not through the pooler) |
| `PG_MIGRATE_URL` | `postgresql://pipeshub_migrate:<PG_MIGRATE_PASSWORD>@postgres:5432/pipeshub` (direct) |
| `PG_NODE_URL` | `postgresql://pipeshub_node_login:<PG_NODE_PASSWORD>@pgbouncer:6432/pipeshub` |
| `MIGRATE_SCHEMA_COMMAND` | `none`: the schema job above already built the tables |

Put them in a file only you can read, for example `migrate.env` with mode `600`, and delete it after the move. The tool never prints the passwords. Load them into your shell and define a short command that runs the tool in a one-off container of the PipesHub image:

```bash
set -a; . ./migrate.env; set +a
docstore() {
  docker compose run --rm --no-deps \
    -e PG_IMPORT_URL -e PG_MIGRATE_URL -e PG_NODE_URL -e MIGRATE_SCHEMA_COMMAND \
    pipeshub-ai node /app/backend/dist/scripts/docstore-migrate.js "$@"
}
```

## 3. Check before you copy

```bash
docstore preflight
```

Preflight only reads. A `red` entry blocks the move and says why: for example a collection the tool cannot map, ids it cannot carry over, or too little disk. On the offline path, `app_running` is red while the API is still connected to MongoDB, which is expected until step 4. `yellow` entries are warnings, such as empty collections the tool does not copy.

## 4. Copy

<Tabs>
  <Tab title="Offline move">
    Stop the API, copy, check every document, and make PostgreSQL the store, in one command:

    ```bash
    docker compose stop pipeshub-ai
    docstore migrate --offline
    ```

    `--dry-run` runs only the preflight. On success the report ends with `"stage": "done"` and "copied and verified; set DOC_STORE=postgres and start the application". MongoDB is then marked retired. Do not start the API on MongoDB again unless you [roll back](#roll-back): what it wrote there would not reach PostgreSQL.

    If the copy or the check fails, the report names the stage and the differences. MongoDB stays the store and nothing is lost. Fix the cause, run `reset --yes` to empty the copied tables, and run the command again.

    Go on to step 6.
  </Tab>
  <Tab title="Online move">
    The API keeps running on MongoDB. Copy, catch up and check:

    ```bash
    docstore migrate --online
    ```

    It ends in `"stage": "online_ready"`. From then on, keep the follower running: it applies every MongoDB change to PostgreSQL, so the copy stays a second or two behind. Stop it with Ctrl+C or `SIGTERM`.

    ```bash
    docstore follow run
    ```

    These examples use the `docstore` command from step 2. On an install that is not managed with Docker Compose, run the same commands in a container of the PipesHub image with the same variables.
  </Tab>
</Tabs>

## 5. Compare in shadow mode (online move)

In shadow mode the API keeps MongoDB as its store, reads it and writes it as before. It also repeats a sample of its reads on the PostgreSQL copy and compares the two answers. Users always get the MongoDB answer. A failed, slow or unreachable PostgreSQL only shows up in the counts, and nothing is ever written to PostgreSQL. The follower from step 4 keeps the copy current.

Restart the API with:

| Variable | Value |
|---|---|
| `DOC_STORE` | `shadow` |
| `PG_NODE_URL` | the node login through the pooler, as in step 2 |
| `DOC_STORE_FENCE` | `on`. Every write first checks the store fence, which the switch in step 6 relies on |
| `DOC_STORE_SHADOW_SAMPLE` | share of reads compared, `0` to `1` (default `0.1`) |
| `DOC_STORE_SHADOW_SETTLE_MS` | wait before a difference is checked again (default `2000`) |
| `DOC_STORE_SHADOW_TIMEOUT_MS` | longest wait for the PostgreSQL answer (default `2000`) |
| `DOC_STORE_SHADOW_MAX_IN_FLIGHT` | most comparisons running at once (default `8`) |

The API logs `document store: mongo, with shadow reads on postgres` when it starts. Use it as usual for a while, so sign-in, people and groups, settings, tokens and projects are all read.

### Read the differences

A difference that is still there when checked again after `DOC_STORE_SHADOW_SETTLE_MS` is logged as a warning from the `DocStoreShadow` service:

```text
shadow read differs between MongoDB and PostgreSQL
metadata: { "repo": "group", "method": "list", "differences": 6,
            "fields": ["$.rows[0]._id", "..."], "ids": ["..."], "idsOnPostgres": ["..."] }
```

- `repo` and `method` name the read; `fields` lists where the answers differ (paths only, never values); `ids` and `idsOnPostgres` are the ids each store returned.
- A difference on a record created a moment earlier, with `idsOnPostgres` empty, means the copy was behind. Raise `DOC_STORE_SHADOW_SETTLE_MS` above the follower's lag (its `lagMs`).
- Any other difference is something to investigate before you switch. Run `verify --incremental` to check every document changed since the last check, or `verify` to check them all.
- If you collect metrics, `docstore_shadow_reads_total{repo,result}` counts the comparisons by result: `equal`, `diff`, `timeout` and `error`.

A clean shadow run and a clean `verify --incremental` are what the switch asks you to confirm.

## 6. Switch the API to PostgreSQL

<Tabs>
  <Tab title="Offline move">
    The copy already made PostgreSQL the store. Start the API with the document-store override, which sets `DOC_STORE=postgres` and the PostgreSQL logins:

    ```bash
    docker compose -f docker-compose.yml -f docker-compose.postgres-docstore.yml up -d pipeshub-ai
    ```

    To keep the override for later `install.sh` runs (upgrades, `--reconfigure`), add it to `.env`:

    ```bash
    PIPESHUB_COMPOSE_OVERRIDES=docker-compose.postgres-docstore.yml
    ```
  </Tab>
  <Tab title="Online move">
    With the follower still running and the API in shadow mode with `DOC_STORE_FENCE=on`:

    ```bash
    docstore cutover --dry-run --fence-armed --shadow-clean
    docstore cutover --fence-armed --shadow-clean
    ```

    - `--fence-armed` confirms that every API process runs with `DOC_STORE_FENCE=on`, and `--shadow-clean` confirms that shadow mode showed no difference. The cut refuses without them.
    - The cut asks running chats to finish, makes MongoDB read-only, applies the last changes, checks them, and makes PostgreSQL the store. Writes pause for a few minutes. `--max-freeze` (seconds, default 600) bounds the pause.
    - If any check fails, the cut puts MongoDB back as the writable store and changes nothing else. `unfreeze` does the same by hand if a cut was interrupted.

    When it reports `"stage": "done"`, restart every API process with `DOC_STORE=postgres`, `PG_NODE_URL` and `PG_JOBS_URL` (the jobs login, `postgresql://pipeshub_jobs:<PG_JOBS_PASSWORD>@pgbouncer:6432/pipeshub`). Then start the reverse follower, which writes every PostgreSQL change back to MongoDB so that an online rollback stays possible:

    ```bash
    docstore reverse
    ```
  </Tab>
</Tabs>

The API logs `document store: postgres` when it starts. Sign in and check your data.

### Close the import login

When the move is done:

```bash
docker compose exec postgres psql -U postgres -d pipeshub -c 'ALTER ROLE pipeshub_import NOLOGIN'
```

`status` warns while the login is left open with no move running. Add the PostgreSQL data volume, `<project>_postgres_data`, to your backups. MongoDB's data stays as it was at the switch. Keep it until you no longer need a rollback.

## Roll back

| Situation | Command | Then |
|---|---|---|
| Offline move, before the API wrote anything to PostgreSQL | `rollback` | Checks that MongoDB still matches PostgreSQL and makes MongoDB the store again |
| Offline move, after the API wrote to PostgreSQL | stop the API, then `rollback --reverse` | Copies every document from PostgreSQL back over MongoDB |
| Online move, with `reverse` running since the switch | `rollback --online` | Writes pause while the last changes go back, then MongoDB is the store again and PostgreSQL is closed |

Run these with the import login open (step 2). Then start the API with `DOC_STORE=mongo`. On Compose, start it without the override file and remove `PIPESHUB_COMPOSE_OVERRIDES` from `.env`. A rollback that cannot verify its copy refuses and leaves PostgreSQL the store.

## Other stores

PipesHub can also keep its configuration, message queue, graph and search vectors in PostgreSQL. Moving the document store does not change them.

| Setting | PostgreSQL value | Existing data |
|---|---|---|
| `KV_STORE_TYPE` | `postgres` | Copy the configuration first with `python -m app.scripts.kv_redis_to_postgres` (in the PipesHub image, from `/app/python`, with `PG_CORE_URL` set and the services stopped). Try `--dry-run` first |
| `MESSAGE_BROKER` | `postgres` | Messages still queued in Redis or Kafka are not moved. Switch when the queues are empty |
| `DATA_STORE` | `postgres` | Not copied. A switch starts with an empty graph |
| `VECTOR_DB_TYPE` | `pgvector` | Not copied. Records need indexing again |

`PIPESHUB_STORE=postgres` sets `KV_STORE_TYPE`, `MESSAGE_BROKER` and related settings to `postgres` wherever they are not set. See [Environment variables](/deployment/environment-variables).

## Known limits

- On the PostgreSQL message broker (`MESSAGE_BROKER=postgres`), stored-record retention stays paused: documents that later writes replaced are not purged yet. This will change in a future release.
- The online move and shadow mode need MongoDB as a replica set. The Docker Compose install uses the offline move.
- Shadow mode compares a sample of the API's reads, and only while the API is not inside a write transaction. It never compares writes. `verify` is the full check.
- Some differences between the stores are expected, and the tool accounts for them:
  - the U+0000 character, which PostgreSQL text cannot hold, is removed;
  - JSON key order is not kept;
  - published outbox events (messages already delivered) are history and are not copied;
  - empty collections the tool does not map are skipped.
- The Kubernetes chart does not set `DOC_STORE` yet. On Kubernetes, set the variables on the API's deployment yourself.
