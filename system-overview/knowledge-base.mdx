# Knowledge Base API

The Knowledge Base Service provides a centralized repository for managing and accessing personal data through files and documents. This service enables document storage, retrieval, and management while integrating with the AI backend for intelligent search capabilities.

## Base URL

All endpoints are prefixed with `/api/v1/knowledgeBase`

## Authentication

All endpoints require authentication via Bearer token:

```http
Authorization: Bearer YOUR_TOKEN
```

## Architecture Overview

The Knowledge Base Service is built on a Node.js backend, with graph-based data persistence in whichever graph database the instance is configured to use (Neo4j by default, ArangoDB as an alternative). The service consists of several key components:

- **Record Management** - Core document storage and metadata handling
- **File Storage Integration** - Connects with external storage services
- **Event Broadcasting** - Kafka-based events for system integration
- **AI Indexing** - Automatic content indexing for search capabilities

The service integrates with these components:

- **Storage Service** - Handles actual file storage and versioning
- **AI Backend** - Processes and indexes content for search
- **Enterprise Search** - Provides search capabilities across the knowledge base
- **IAM Service** - Handles user authentication and authorization
- **Configuration Manager** - Manages application settings

## Data Models

### Records

Records represent the core entities in the knowledge base:

- Metadata about stored content (name, type, source)
- References to physical files in storage
- Versioning information
- Indexing status and history

### File Records

File Records contain file-specific metadata:

- File format information (extension, MIME type)
- Size and storage information
- Access URLs and paths
- Checksum and integrity information

### Knowledge Base

Knowledge Base represents a collection of records:

- Organizational grouping of records
- Permission structure
- Metadata about the collection

<Accordion title="POST /:kbId/upload - Upload to Knowledge Base or Folder">
Upload files to the root of a knowledge base, or into one of its folders, creating records and folder structures as needed.

<Tabs>
<Tab title="Request">
**Endpoint:** `POST /api/v1/knowledgeBase/:kbId/upload`

**Path Parameters:**

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| kbId | string | Yes | Knowledge base UUID |

**Query Parameters:**

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| folderId | string | No | Folder to upload into. Leave it out to upload to the knowledge base root. |

**Request Body Parameters:**

| Parameter | Type | Required | Description |
|-----------|------|----------|-------------|
| files | file[] | Yes | Files to upload (max 1000 files, 30MB per file by default) |
| files_metadata | string | No | A JSON array with one `{ "file_path": string, "last_modified": number }` entry per file, in the same order as `files`. `file_path` places the file in folders (for example `folder/report.pdf`), and `last_modified` is in milliseconds. Without it, each file is placed directly in the target under its own name. |
| isVersioned | boolean | No | Whether files should be versioned (default: true) |

**Content-Type:** `multipart/form-data`

**File Constraints:**
- Maximum files per upload: 1000
- Maximum file size: 30MB per file
- Supported MIME types: Based on extensionToMimeType mapping
- File paths must be unique and not contain invalid characters

```bash
curl -X POST \
  -H "Authorization: Bearer YOUR_TOKEN" \
  -F "files=@document1.pdf" \
  -F "files=@folder/document2.docx" \
  -F 'files_metadata=[{"file_path":"document1.pdf","last_modified":1714208400000},{"file_path":"folder/document2.docx","last_modified":1714208500000}]' \
  -F "isVersioned=true" \
  /api/v1/knowledgeBase/kb123456/upload
```

To upload into a folder instead, add its ID as a query parameter: `/api/v1/knowledgeBase/kb123456/upload?folderId=folder456`.
</Tab>

<Tab title="Response">
**Status:** `200 OK`

**Content-Type:** `text/event-stream`

The response is a stream of [Server-Sent Events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events). The server sends one `file:succeeded` or `file:failed` event for each file as soon as that file is settled, then a final `done` event with a summary, and then closes the stream.

| Event | When it's sent | Fields in `data` |
|-------|----------------|------------------|
| `file:succeeded` | The file was stored and its record was created. Indexing carries on in the background. | `recordId`, `fileName`, `filePath`, `extension` |
| `file:failed` | The file wasn't added. The other files in the upload still go ahead. | `fileName`, `filePath`, `extension`, `errors` (a list of messages), `stage` (`upload` or `index`), plus `recordId` once one was assigned and `reason` when there is one (`EXCEEDS_SIZE_LIMIT`, `UNSUPPORTED_TYPE` or `DUPLICATE_NAME`) |
| `done` | The last event, once every file has its own event. | `summary` with `total`, `succeeded` and `failed` counts |
| `error` | Something went wrong after the stream had started. The stream closes right after it, so treat any file that didn't get its own event as failed. | `message` |

```text
event: file:succeeded
data: {"recordId":"rec789012","fileName":"document1.pdf","filePath":"document1.pdf","extension":"pdf"}

event: file:failed
data: {"fileName":"document2.docx","filePath":"folder/document2.docx","extension":"docx","errors":["This file is larger than the 30 MB limit. Make it smaller or split it, then upload it again."],"reason":"EXCEEDS_SIZE_LIMIT","stage":"upload"}

event: done
data: {"summary":{"total":2,"succeeded":1,"failed":1}}
```

Lines that start with a colon, such as `: keepalive` (sent about once a second while work is in progress), only keep the connection open and can be ignored. Problems found before the stream starts, such as a missing token, no permission to write to the knowledge base, or a knowledge base or folder that doesn't exist, come back as an ordinary JSON error with a `4xx` status instead of a stream.
</Tab>

<Accordion title="Administrative Operations">
Connector statistics, reindexing and resync are not part of the Knowledge Base API. They are in the Connectors API, under `/api/v1/connectors`, and take a connector instance ID:

- `GET /api/v1/connectors/:connectorId/stats` - Indexing statistics for a connector. Needs only the ID.
- `POST /api/v1/connectors/:connectorId/reindex` - Reindex a connector's records. The body is optional: send `{ "statusFilters": [...] }` to reindex only the records with those indexing statuses.
- `POST /api/v1/connectors/:connectorId/resync` - Resync a connector's records. The body must include `connectorName` (the connector's name), and may include `fullSync: true` for a full resync. A request without `connectorName` is refused.

The Knowledge Base API's old `stats/:connector`, `reindex-all/connector` and `resync/connector` endpoints no longer exist.
</Accordion>

## Event System

The Knowledge Base Service broadcasts events through Kafka to notify other services about record changes. These events trigger actions like content indexing, search updates, and audit logging.

### Event Types

| Event Type | Description |
|------------|-------------|
| `newRecord` | Triggered when a new record is created |
| `updateRecord` | Triggered when a record is updated |
| `deletedRecord` | Triggered when a record is deleted |
| `reindexRecord` | Triggered when a record needs reindexing |

**Common Error Codes:**
- `400 Bad Request` - Invalid request parameters, file validation errors
- `401 Unauthorized` - Missing or invalid authentication
- `403 Forbidden` - Insufficient permissions
- `404 Not Found` - Resource not found
- `413 Payload Too Large` - File size exceeds limit
- `422 Unprocessable Entity` - Validation errors
- `500 Internal Server Error` - Server errors, backend service failures

**File Upload Specific Errors:**
- File extension mismatch for versioned updates
- Unsupported MIME types
- File size exceeds 30MB limit
- Invalid file path characters
- Duplicate file paths in upload

## Integration with AI Indexing

When a record is created or updated, the Knowledge Base Service:

1. Stores the file metadata in the graph database
2. Uploads the file content to the Storage Service
3. Publishes a Kafka event with the file metadata and download URL
4. The AI Backend consumes these events and:
   - Downloads the file content
   - Extracts text and structured data
   - Processes the content for search indexing
   - Updates the indexing status in the Knowledge Base

This integration enables Enterprise Search to provide intelligent search capabilities across the entire knowledge base.

## Security and Permissions

- All endpoints require valid JWT authentication
- Admin endpoints require additional role verification
- File uploads are validated for MIME type and size
- Access control is enforced at the organization level
- File content is streamed securely through signed URLs
- Upload paths are sanitized to prevent directory traversal

## Rate Limits and Constraints

- **File Upload**: Maximum 30MB per file by default (set in platform settings), 1000 files per upload
- **Pagination**: Maximum 100 items per page
- **Search Terms**: Maximum 1000 characters
- **Knowledge Base Names**: 1-255 characters
- **File Paths**: Must not contain invalid characters or be duplicated
