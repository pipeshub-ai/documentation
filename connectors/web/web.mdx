## Overview

The Web connector ingests **publicly reachable** pages and files from a website you specify. It fetches content over HTTP(S) like a browser, with configurable crawl scope and limits. 
You can index a **single page** or use **recursive** mode to discover more pages by following links.

## Configuration setup

<AccordionGroup>

<Accordion title="Setup guide" icon="gear">

### Step 1: Create a Web connector

In PipesHub, add a Web connector instance. There are two scopes to choose from: **personal** and **team**. 

You can create a **personal** connector from Workspace Settings > *Your Connectors* > Web > Setup. The records created by this connector will be visible to you only.

You can create a **team** connector from Workspace Settings > *Connectors* > Web > Setup. The records created by this connector will be visible to all users in your organization. This connector can be created by Admins only.

### Step 4: Crawl type and limits

| Field | Description |
|--------|-------------|
| **Crawl type** | **Single** — one URL only. **Recursive** — follow links extracted from each page’s HTML, subject to host, depth, path rules, and your caps. |
| **Crawl depth** | Maximum link depth to which pages are crawled. |
| **Maximum pages** | Upper bound on how many distinct URLs are processed during sync. |
| **Maximum Size in MB (default 10MB)** | Largest HTTP body to download per URL, from 1 to 100 MB. A larger file isn't downloaded. If PipesHub doesn't have that address yet, it is listed as a failed page with the reason, so you can raise the limit if you need it. A file PipesHub already has keeps its stored copy (the last version that fit) when it grows past the limit. |
| **Follow external links** | When enabled, links to **other domains** may be followed. When disabled, crawling stays on the **same host** as the start URL. Disabled by default. |
| **Restrict to start path** | When enabled, only URLs whose path stays **under** the starting path prefix are crawled (useful for subsites). If this is on, **Follow external links** is effectively off—you cannot combine path restriction with arbitrary external domains. |
| **URL should contain** | Optional tags: if any are set, only URLs containing **at least one** of the substrings (case-insensitive) are synced—except the **configured start URL**, which is always allowed. |
| **Robust Mode (slower)** | Fetches pages with a real Chromium browser. Turn it on for sites that build their pages with JavaScript or block simple requests. Documents such as PDFs are still downloaded directly, so the file itself is stored rather than the browser's viewer page. Off by default. |
| **Respect robots.txt** | Skips pages that the site's `robots.txt` asks crawlers not to visit. On by default. See **robots.txt** under Connector Workflow below. |

<Note>
  **Respect robots.txt** is on for existing Web connectors too. If a site's `robots.txt` blocks crawlers, the next sync skips the pages it disallows, and a site that blocks crawlers entirely syncs nothing until you turn the setting off. Pages that were already synced stay in PipesHub; they just aren't fetched again.
</Note>

### Step 5: Filters and indexing

- **Enable manual sync filter:** This allows you to have control over which records are indexed. It stops records from being automatically indexed. You can then go to **All Records** section to index the records manually.
- **File extension filter:** Restrict which file extensions are synced and skipped. Pages of excluded types are still read for their links, so a filter such as "PDF only" still finds the PDFs that HTML pages link to; the excluded pages just aren't stored.
- **Indexing toggles:** Turn indexing on or off by category for **webpages**, **images**, and **documents** (and related options shown in connector settings) to control what downstream search indexing receives.

## Connector Workflow

<AccordionGroup>

<Accordion title="How Web connector works" icon="globe">

### What the connector does

- **Crawling:** Starts from your configured **Website URL**. In recursive mode, discovers links from HTML, resolves them against the page URL, and visits URLs that pass validation (scheme, domain, path, extension, and optional URL substring filters).
- **Fetching:** Uses a **multi-strategy** HTTP pipeline (standard client, then browser-like TLS profiles and fallbacks where available) to improve success on sites that use bot detection or CDN challenges. Requests use realistic browser headers and respect a per-response **maximum size** cap.
- **Content types:** Treats HTML as web pages (title and cleaned text are derived for indexing). Also supports common **documents** (for example PDF, Office formats, CSV, JSON, XML, Markdown) and **images** (with processing for some formats in HTML context). Extension and indexing filters can narrow what is stored or sent for indexing.
- **Structure:** Builds a **record group** for the configured root URL and **file records** per URL, with parent links so paths appear hierarchically where applicable. URLs are **normalized** to avoid duplicate records: trailing slashes on “directory” pages, `#section` parts of links, and the order of query-string parameters (`?a=1&b=2` and `?b=2&a=1` are one page) don't create separate records.
- **Redirects:** A page that redirects is stored once, under the address it lands on. A redirect that leaves the site is treated as an external link.
- **Changes:** On later syncs, the connector sends back the site's `ETag` and `Last-Modified` values for documents, in both modes. Web pages get them only in a normal crawl (Robust Mode off), and only when their links aren't needed: a single-page crawl, or pages at the crawl's depth limit. When the site answers "not changed" (304), nothing is downloaded or re-indexed. Every other page is downloaded in full on each sync, including every web page in Robust Mode, and a page whose text hasn't changed isn't re-indexed. When a file moves to a new address, the first sync that sees the redirect downloads it normally and stores it there, because the new address has no stored values yet. After that, a "not changed" answer from the new address is trusted when it matches the stored copy (by `ETag` when the answer has one, otherwise by `Last-Modified`), and nothing is downloaded. The file is downloaded again only if the "not changed" answer came in reply to the old address's values, which happens on sites that refuse header-only requests. The old address is removed on the second sync that sees the redirect, like other moved pages.
- **Pages that are gone:** When a page answers **404 Not Found** or **410 Gone** on **two syncs in a row**, its indexed copy and stored file are deleted, so it drops out of search. Two strikes allow for a site that briefly answers 404 during a deploy. The address then stays in **All Records** as a failed page with nothing indexed. It stays there even after the site stops linking to it, because the crawler only removes pages it visits, and a page that is no longer linked is kept as it is. An old address that now redirects to another stored page (or several old addresses that all redirect to the same page) is handled differently: on the second sync that sees the same redirect, the old address is removed completely, with no failed page left behind, even if the site still links to it. The page itself is kept under the address it lands on. Temporary problems (a 5xx error, a 429, a 403, a timeout, or the whole site being down) never remove anything, and nothing is removed in a sync where the start page itself is gone, whether it answers 404 or 410 directly or after a redirect. When a page that other links redirect to is removed, any older records stored under those redirecting links are removed with it.
- **Sync:** Supports **scheduled** sync (default daily) and connector **filters** (manual sync selection, file extensions, and indexing toggles in the product UI). **Team** vs **personal** scope controls who receives permissions on synced records.

### Key limitations

- **Public content only:** Anything that requires login, cookies, or private APIs is out of scope unless the URL returns the content without authentication.
- **Rate limits and terms of use:** Respect your own policies and the target site’s terms of use. Heavy crawling can trigger **429** or blocks; the connector retries some transient errors with backoff but cannot guarantee access to every site.
- **Starting URL is fixed:** After creation, the root **Website URL** (and its domain) **cannot** be changed; create a new connector for a different site or domain.

</Accordion>

<Accordion title="robots.txt" icon="robot">

### robots.txt

With **Respect robots.txt** on (the default), the connector reads each site's `robots.txt` once per sync and follows it the way the robots.txt standard (RFC 9309) describes:

- Rules written for **PipesHub** by name (`User-agent: PipesHub`) apply if the site has them. Otherwise the rules for all crawlers (`User-agent: *`) apply. The requests themselves still carry a browser-like `User-Agent` header, so a site's server logs won't show the name PipesHub.
- The most specific (longest) matching rule decides, and `Allow` wins a tie. The `*` and `$` wildcards are understood.
- A `robots.txt` that is missing, or that the site refuses with a 4xx error other than 429, allows everything.
- A `robots.txt` that can't be read (a 5xx error, a 429, or no answer within 10 seconds) means that site isn't crawled in this sync. Its stored pages are left as they are, and it is tried again on the next sync.
- A group for **PipesHub** that lists no rules allows everything, even if the `*` group disallows pages.
- The rules also apply to redirects. A redirect's target is checked against the crawl's scope and `robots.txt`, and a target that is disallowed, or outside the crawl, is never stored or indexed. A disallowed one counts toward the skipped pages in the summary. Whether the target is even requested depends on the case:
  - **Normal crawl (Robust Mode off):** each redirect is checked before it is followed, so a disallowed or out-of-scope target isn't requested. If the site refuses, fails or doesn't answer header-only (`HEAD`) requests, that check is skipped and the redirect is followed as before: a disallowed or out-of-scope target is then requested and dropped, and an allowed target is fetched and stored as usual.
  - **Documents in Robust Mode:** a redirect onto a file is checked before the file is requested, so a disallowed or out-of-scope file gets no request at all. This holds even when the site refuses `HEAD`: that step is retried with a `GET` that doesn't follow the redirect.
  - **Web pages in Robust Mode:** the browser follows redirects on its own, so the connector first walks each page's redirects with the same check files get: a header-only (`HEAD`) request per step, or a `GET` that doesn't follow the redirect when the site refuses or fails `HEAD`. A target this check turns down is never loaded. When the check can't finish (the site doesn't answer it, or is still redirecting after 10 requests), the browser loads the page anyway. The same goes for a redirect the site sends only to the browser. If the browser then lands on a page that is disallowed or outside the crawl, that page is dropped and never stored; an allowed landing is kept, like any other redirect. The check adds at least one request per page.

The summary at the end of each sync says how many pages robots.txt caused to be skipped, and names any site whose `robots.txt` couldn't be read. To include the skipped pages, turn off **Respect robots.txt** in the connector settings, if the site's terms allow it.

## FAQ

<AccordionGroup>

<Accordion title="The site returns 403 or blocks the connector. What can I do?">

Many sites use bot protection (CDNs, CAPTCHAs, or geographic rules). The connector tries multiple fetch strategies, but **no integration can guarantee** access. Try a simpler entry URL, reduce crawl rate by lowering scope (URL filters, single-page mode), or host documentation on a domain that allows automated access. Sites that require interactive login cannot be indexed with this connector alone.

</Accordion>

<Accordion title="Why did my crawl stop at fewer pages than the maximum?">

Common reasons include: **maximum pages** or **depth** reached, **URL should contain** filtering out branches, **same-domain** rules excluding external links, **path restriction** excluding parent or sibling paths, the site's **robots.txt** disallowing pages (the end-of-sync summary gives the count), **extension** filters, **size** limits skipping large files, non-retryable HTTP errors (for example **404**), or links pointing only to asset types the crawler does not follow as pages.

</Accordion>

<Accordion title="Why do some pages show as failed?">

A page that can't be synced is listed as a failed record in **All Records**, with the reason and what to do next. A site with many broken links will therefore show many failed pages. When a link redirects before failing with a 404, 410 or 401, or to a file over the size limit, the failed record is filed under the address that gave that answer. A 403, 408, 429, 5xx or a connection failure after a redirect stays filed under the link that was crawled. The reasons you may see:

| Reason shown | What it means |
|---|---|
| The page wasn't found (404 Not Found). Check the URL is correct, then sync again. | The link points at a page that doesn't exist. |
| The page wasn't found (410 Gone). Check the URL is correct, then sync again. | The site says the page was removed for good. |
| The page refused access (401 Unauthorized). It may need a login or block automated visitors; make sure it's publicly reachable, then sync again. | The page needs a login. Only publicly reachable pages can be synced. |
| The page refused access (403 Forbidden). It may need a login or block automated visitors; make sure it's publicly reachable, then sync again. | The page needs a login, or the site blocks automated visitors. |
| This file is larger than this connector's 10 MB size limit, so it wasn't downloaded. Raise the Maximum Size in MB setting to include it, then sync again. | The file is over **Maximum Size in MB**. The message shows the limit this connector is set to (10 MB unless you changed it). |
| We couldn't reach this page. Check the URL is correct and publicly reachable, then sync again. | The server never answered with a status at all (the connection failed or timed out). |
| The site didn't respond properly (503 Service Unavailable). PipesHub will try again on the next sync. | A temporary problem on the site's side. The same message is used, with the status filled in, for 408 Request Timeout, 429 Too Many Requests and every status of 500 or above. A code that isn't a standard HTTP status, such as the CDN codes 520 to 529, is shown as a bare number, for example "The site didn't respond properly (522)." |
| The page returned an error (418 I'm a Teapot). Check the URL is correct and publicly reachable, then sync again. | Any other error status below 500. The status and its name are filled in; 418 is only an example. A non-standard code below 500 is shown as a bare number. |

The status shown is the one the site actually sent, in Robust Mode too, with its standard name when it has one and as a bare number when it doesn't. For a 401, 403, 408, 429, 5xx, a timeout, or a file that has grown past the size limit, a page that synced before keeps its record and indexed copy; the failure never replaces it, and no failed page is added for it. A 404 or 410 is different: on the second sync in a row, the synced copy is deleted and the failed page takes its place (see **Pages that are gone** above).

</Accordion>

<Accordion title="Can I change the website URL after setup?">

No. The root URL and domain are fixed for the lifetime of the connector instance. To index a different site or domain, **create a new Web connector**.

</Accordion>

<Accordion title="How are permissions applied?">

For **team** scope, records are readable at the organization level as configured by PipesHub. For **personal** scope, ownership-style permissions are tied to the user who created the connector. Exact behavior matches your workspace’s connector permission model.

</Accordion>
